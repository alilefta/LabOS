# N-FILE-110 first clinical attachment — architecture decision

Status: accepted first-attachment design after independent V3 `PASS | ARCHITECTURE/DECISION` review. Scope: first attachment of one finalized S001 evidence/grant pair; design only. The S001 finalizer remains independently `PASS | CODE/ARCHITECTURE + RUNTIME_EVIDENCE/CHECKPOINT`. N-FILE-110 remains inactive and live provider/Case flow remains `NOT_RUN`.

## Installed facts that determine the design

- `FileUploadGrant` has `PENDING`, `UPLOADED`, `CONSUMED`, `EXPIRED`, `FAILED`, `CLEANED`, with `uploadedAt`, `consumedAt`, `expiresAt`, provider key, Case target, creator Member and immutable checked suffix. The accepted finalizer inserts immutable evidence and moves exactly `PENDING -> UPLOADED` atomically. Generic `expireDue` can mark an expired `UPLOADED` grant `EXPIRED`.
- `CaseClinicalUploadEvidence.uploadGrantId` is the PK. Its composite FK binds the exact grant, tenant, provider and `providerObjectKey`; the installed trigger additionally binds Case, purpose, suffix and live reservation at insertion. It has exact measured size/SHA, S001 implementation identity and validation time. Evidence cannot be updated or deleted.
- `StoredFile.id` is the application file identity. `sourceUploadGrantId` and `(provider, providerObjectKey)` are each unique. Its tenant-aware FK links the source grant; `providerAccess` classifies the immutable physical object. It has no URL column. The installed trigger prevents mutation/deletion except the existing live-Member-to-null transition.
- `CaseAssetFile.id` is the stable Case asset identity. The installed composite Case/Lab FK, `storageMode`, `clinicalPurpose`, nullable `currentVersionId` and managed final-state triggers govern its representation. `CaseAssetFileVersion` is immutable, uniquely references a `StoredFile`, has unique `(caseAssetFileId, versionNumber)`, and is the tenant-aware bridge to the asset. The composite current-version FK requires the pointer to name a version of this asset and Lab.
- The public-backed V1 mode is `MANAGED_PUBLIC` plus `StoredFile.providerAccess = PUBLIC_READ`. New managed pointers require matching immutable clinical evidence through the installed deferred trigger. Ordinary Case DTOs omit provider URL/key; public-open is a separate freshly authorized operation. The existing public-open code checks grant/evidence identity but does not currently require `grant.status = CONSUMED`; activation verification must close that predicate without changing public URL policy.
- The generic upload-grant `consume` repository is not directly reusable: it requires nonnull `providerFileUrl`, while an N-FILE-110 Case grant deliberately has no authoritative URL. A Case-specific transaction may reuse its serializable/conditional-consumption pattern, not its URL-bearing result contract.

## Decision

### 1. Preconditions before provider network work

A server-only first-attachment operation takes an opaque grant ID as a selector, never tenant, Case, provider key/URL, suffix or evidence facts as caller authority. It validates the identifier and resolves the exact grant, evidence, Case/Lab/Organization and creator Member from the database. Before retrieval it requires: boundary `N-FILE-110`, purpose `case.asset.add.stage`, target `case`, exact `UPLOADTHING` reserved key, no authoritative grant URL or provider-deleted marker, nonnull checked suffix, status `UPLOADED`, `uploadedAt` set, `consumedAt` null, no terminal failure/expiry marker, and database-current time strictly before `expiresAt`. Evidence must be the exact one-to-one successful S001 row, match grant/tenant/Case/provider/key/suffix, and carry the approved S001 identity, positive measured length and lowercase SHA-256. The Case must still be saved `DRAFT` in the canonical Lab/Organization. The grant creator must still be an active canonical Member with current `case.asset.add` authority and any required active Staff assignment. No `StoredFile` for the grant/key, no first version, and no conflicting managed asset may exist. Local invalidity fails before provider access.

The operation is server-controlled; an interactive caller cannot substitute a different actor. The **grant creator** is the attachment actor, as in finalization. If an eventual interactive route accepts the grant ID, it must first bind the authenticated current Member to that creator; an internal continuation may derive the same creator from the grant. Both paths freshly recheck that Member's authorization. `uploaderMemberId`/`createdByMemberId` use the live creator, with immutable ID snapshots retained per the installed schema. A removed/revoked creator fails closed; a different authorized Member cannot take over this grant under this V1 decision.

### 2. Exact retrieval and byte equality

Reuse server-only `retrieveReservedUploadThingBytes(grant.providerFileKey)` from `jpeg-r001/retrieve.ts`. Its UploadThing key lookup requires one exact returned key, the attested HTTPS origin/path, public-address DNS answers pinned into the TLS-verified request, no redirect or nonidentity encoding, complete `200`, bounded streaming to 33,554,432 bytes, and generic failure. No callback/client URL or provider metadata becomes retrieval authority. The returned private `Buffer` is the sole comparison input. Require `BigInt(buffer.length) === evidence.measuredSizeBytes` and SHA-256 of those same original bytes equals `evidence.contentSha256`; check the length before hashing. Failure, including disappearance, truncation or provider content change, creates no asset row and does not consume the grant. Do not rerun S001 or accept a different JPEG that merely passes S001. Do not persist the retrieved URL or bytes. Recompute the same private Buffer's length/SHA immediately before the write transaction if it remains retained across other asynchronous work; no second provider fetch is substituted for this attempt.

This equality proves what this retrieval returned at the attachment check. The provider probe did not establish permanent object immutability; the public object may change or disappear after commit. Existing public-open behavior and future provider policy must not describe the object as permanently immutable.

### 3. Transaction-fresh TOCTOU closure and atomic writes

After equality, open one serializable transaction. Lock the exact grant row `FOR UPDATE` before checking consumption; lock the target Case and freshly read the evidence, Lab and creator Member. Re-establish every pre-network identity, suffix, `UPLOADED`/live/eligible state, no `StoredFile`/version conflict, Case `DRAFT` status and current transaction-compatible `case.asset.add` policy/assignment. Compare the fresh evidence size/SHA to the bytes already matched and its exact profile/identity to the pre-network snapshot; evidence immutability is a second defense, not permission to omit the recheck. Do not hold database locks over network work.

Within that same transaction, create exactly one `StoredFile` with generated application ID, canonical tenant/Lab, `sourceUploadGrantId`, fresh grant provider/key, `purpose = CASE_CLINICAL_ASSET`, `providerAccess = PUBLIC_READ`, `detectedMimeType = image/jpeg`, `sizeBytes` from evidence, and an allowlisted `SHA-256` checksum/value equal to evidence. Set uploader live Member and immutable Member-ID snapshot from the grant creator. Create a new `CaseAssetFile` for that Case/Lab with `assetFileType = IMAGE`, `storageMode = MANAGED_PUBLIC`, evidence clinical purpose, null legacy `documentUrl`/`fileExtension`, and initially null current pointer. Create immutable `CaseAssetFileVersion` number **1** for the new asset and `StoredFile`, creator Member/snapshot as above; then set that asset's `currentVersionId` to the new version. Finally conditionally update the exact `UPLOADED` grant to `CONSUMED` and set `consumedAt` using server/database time, requiring one row. Commit all writes together. The managed final-state trigger is deferred and re-reads the final asset; it permits the transient null pointer inside the transaction only when the final pointer, public access and matching evidence are present at commit. Failure anywhere rolls back StoredFile, asset, version, pointer and grant consumption together. Evidence is read only and never gains an asset ID or attachment timestamp.

The provable evidence link is `version.storedFileId -> StoredFile.sourceUploadGrantId -> CaseClinicalUploadEvidence.uploadGrantId`, plus exact provider/key/tenant/Case/purpose checks in the installed managed-pointer trigger. No direct redundant evidence FK is needed for V1. The current schema supports this first attachment without migration. It does **not** itself constrain every possible direct SQL writer to update grant status when creating a StoredFile; the sole approved application writer must make the conditional `CONSUMED` transition in the same transaction, and all other application paths must reject an inconsistent status/file pair. Additional database-wide hardening would require a separately justified additive trigger decision, not a fabricated field in this gate.

### 4. Durable intermediate state, retries and concurrency

**Yes, but time bounded:** `UPLOADED` + matching immutable evidence + no StoredFile/version + live grant is the durable unattached state. It survives a request/process failure and can be retried by the same authoritative creator while `expiresAt` is still in the future and Case/authorization/provider equality remain valid. Every retry performs a fresh exact-key retrieval and byte equality check. There is no idempotent success after attachment. `CONSUMED` + nonnull `consumedAt` + unique StoredFile/version/current asset is the attached state. `UPLOADED` with a StoredFile, `CONSUMED` without the canonical asset chain, or other partial/inconsistent combinations fail closed for investigation. An `EXPIRED` grant is not attachable; the existing expiry path can end the retry window, and no TTL extension or evidence reuse under a new grant is implied.

Two contenders may both perform bounded retrieval. The grant row lock and exact conditional `UPLOADED -> CONSUMED` ensure one transaction wins; the other re-reads stale/consumed state and fails generically. Database uniqueness on `StoredFile.sourceUploadGrantId`, `(provider, providerObjectKey)`, `CaseAssetFileVersion.storedFileId` and `(caseAssetFileId, versionNumber)` independently prevents duplicate first physical/version identity. No process-local lock is the concurrency guarantee. A stale retry after successful attachment does not create another asset or report a fresh success.

### 5. Failure, cleanup and backward compatibility

Any missing/ambiguous key lookup, untrusted URL, DNS/TLS failure, redirect, non-200/206, content encoding, over-limit/incomplete body, length/SHA mismatch, expired/revoked grant, changed Case/assignment, conflicting asset, or database/trigger failure returns a generic bounded unavailable result. No asset persistence occurs on pre-transaction failure; transaction failure rolls back all application writes. Do not expose provider key/URL, bytes, hash, native details or database diagnostics in ordinary DTO/errors/logs. The provider object is not deleted by database rollback.

If evidence is finalized but attachment fails, the `UPLOADED` grant/evidence remain for a permitted bounded retry; the object may remain provider-side. Expiry/orphan/rejected-object cleanup owns any eventual provider deletion under a separate decision, with exact object identity and no deletion of unrelated objects. Existing legacy URL assets remain unchanged and are not backfilled from URL strings. Historical null-suffix grants, non-S001 evidence, missing or terminal grants, and prior inconsistent asset rows are not silently adopted. Current development counts from earlier checkpoints are historical observations, not a new database inventory.

## Successor verification requirements

A separately authorized first-attachment CODE + disposable PostgreSQL gate should test: all local preconditions before provider access; grant-creator and Staff assignment continuity; exact retrieval adapter invocation only with fresh reserved key; 0/multiple/wrong key and transport failures; exact length/SHA equality and limit; changed bytes/disappearing object; no URL/key in DTO; pre/post-network Case, Member, grant, suffix and evidence changes; no second S001 decode; first version number/pointer and exact StoredFile fields; public access classification; no legacy URL; installed FK/deferred evidence and managed-pointer triggers; every rollback point; duplicate/stale/expired retry; genuine concurrent separate-connection attachment race; evidence immutability; generic errors; no provider deletion; and public-open rejection of any inconsistent non-`CONSUMED` asset chain before activation. The disposable runtime must use the installed schema with synthetic fixtures; provider transport may be injected under controlled tests. Live UploadThing/Case runtime and route activation remain later separate gates.

## Review

Independent V3 verdict: **PASS | ARCHITECTURE/DECISION**. The read-only reviewer inspected the actual Prisma models, C2/public-access/evidence/suffix migrations, exact-key retrieval, S001 finalizer/resolver, generic consume path, public-open, and accepted Files decisions. It found no material defect in the authority, equality, transaction, concurrency, lifecycle, or schema-sufficiency design. The reviewer specifically confirmed that public-open must require `CONSUMED` before later activation. This review establishes a design decision only; first-attachment CODE, disposable runtime, live provider/Case flow, and route activation remain `NOT_RUN`. No application, schema, migration, database or provider operation was performed in this decision gate.

**Single successor gate:** separately authorized first-attachment CODE and disposable PostgreSQL verification of the approved transaction and its provider retrieval/equality boundary. Do not activate N-FILE-110 or perform live provider operations in that successor without separate authority.
