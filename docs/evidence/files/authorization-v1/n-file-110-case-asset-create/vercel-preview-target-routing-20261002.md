# Vercel Preview target-routing resolution

Date: 2026-10-02. Scope: read-only routing investigation; no Vercel or application mutation.

## Resolution and evidence

**Verified platform rule.** Vercel's current [Environments guide](https://vercel.com/docs/deployments/environments#first-deployment) says the first deployment of a new project is always Production, including CLI deployments without `--prod` and deployments from a non-production Git branch. Its [CLI project guide](https://vercel.com/docs/projects/deploy-from-cli#4-deploy-a-preview) says subsequent `vercel deploy` calls create Preview deployments. The [deploy reference](https://vercel.com/docs/cli/deploy#prod) repeats the first-deployment rule and documents `--target` for Preview/Production/custom environments. A [Vercel staff response](https://community.vercel.com/t/vercel-cli-ignores-target-preview-and-creates-production-deployment/46384/7) confirms normal first-deployment Production classification and reports subsequent `--target=preview` working in the staff reproduction. A separate [CLI issue](https://github.com/vercel/vercel/issues/17069) is user-reported corroboration, not a platform guarantee. No CLI 62.1.0 source-level proof of the server's target-resolution branch was established; the current official rule and the retained 62.1.0 result are sufficient to explain this case.

The [stopped probe packet](vercel-s001-preview-20261001/packet.md) records creation of a fresh run-owned project with zero prior deployments, followed by `vercel@62.1.0 deploy --target=preview` from its isolated harness. The retained [deployment inspection](vercel-s001-preview-20261001/failed-deployment-inspect.txt) says `target production`, `status Error` for `dpl_3E1TFf8Unf8FVDup55JihWapYshE`; no function ran. This is exactly the platform's first-deployment pattern. The failed build and subsequent deletion leave no initialized project to reuse. Its build diagnostics were not retained as raw logs and do not establish a native-loading result. Project and deployment cleanup remain as recorded in that historical packet.

**Classification:** the fresh-project first-deployment explanation is **verified as current documented Vercel behavior** and strongly explains the retained result. The precise server-side handling of that particular CLI request was not traced. The prior `VERIFICATION_ENVIRONMENT_BLOCKER` remains the truthful stopped-experiment outcome; this research resolves its routing cause but does not turn either backend's Preview feasibility into PASS.

## Routing options

| Option | Finding |
| --- | --- |
| A. First-deployment placeholder | **Recommended.** Create a newly named isolated project, explicitly protect it, then make a tiny inert first deployment with `--prod --skip-domain`. The [deploy reference](https://vercel.com/docs/cli/deploy#skip-domain) says this prevents automatic production-domain aliasing and requires `--prod`. Retain a successful placeholder while deploying the synthetic harness second with `--target=preview`. Vercel staff explicitly suggested the staged placeholder and retaining the first deployment until after the second. The placeholder is still classified Production *within the run-owned synthetic project*; it is not the LabOS production project or a clinical application. |
| B. Reuse an initialized run-owned project | Viable only after verifying its exact team/project identity, prior successful Production initialization, protection, absent secrets/integrations, and no LabOS link. The prior project's cleanup makes this unavailable now. It provides no stronger target guarantee than A and increases risk of reusing a project with unknown configuration. |
| C. Isolated Git non-production branch | Not a way around the first-deployment rule: the [Environments guide](https://vercel.com/docs/deployments/environments#first-deployment) explicitly includes first deployments from a non-production branch. Later non-production commits normally produce Preview, but creating a separate Git repository/integration adds state and upload paths without improving this experiment's isolation. |

[Project creation](https://vercel.com/docs/cli/project) and [linking](https://vercel.com/docs/cli/link) are separate from deployment creation. They allow pre-upload inspection of team, project, configuration, environment-variable *names/counts*, domains, integrations, and protection. They do not mark a zero-deployment project initialized. No supported way to make a fresh project's first deployment Preview was found in the current docs or staff response.

## Recommended exact retry gate (requires separate authorization)

1. Recheck CLI account/team and establish a new collision-resistant run-owned project name and isolated source directory. Confirm the LabOS project is not linked, selected, or an upload source. Create and link only the new synthetic project; attest its exact project ID, empty deployments, absent LabOS variables/integrations/custom domains, and expected framework/runtime.
2. Before any deployment, enable and verify **Vercel Authentication / All Deployments** for that exact project. Vercel's [2026-09-09 change](https://vercel.com/changelog/protect-production-deployments-for-free-on-every-plan) says this can protect even Production domains on every plan. Older [protection documentation](https://vercel.com/docs/deployment-protection) still describes narrower plan availability, so actual account UI/API capability must be checked; stop if All Deployments protection cannot be attested. Keep the placeholder inert and free of secrets even when protected.
3. Deploy only a static, run-marked inert placeholder as the **first** deployment with explicit run-owned scope/project and `--prod --skip-domain`. Do not include either decoder, a probe endpoint, patient/Case data, environment variables, or provider/database access. Retain the successfully initialized Production placeholder. Inspect its exact project ID, `target production`, readiness, aliases, and protection. Any unexpected alias/exposure stops the run.
4. Re-run the bounded local source/lockfile/upload-manifest preflight for the existing synthetic S001 harness. Address the previously observed remote TypeScript dependency failure within the separately authorized retry's bounded build-repair scope; do not call a failed build a backend failure. Upload the harness as a **second** deployment with explicit run-owned scope/project and `--target=preview` (no `--prod`).
5. Before invoking `/api/probe`, use read-only [deployment inspection](https://vercel.com/docs/cli/inspect) and project deployment listing to require exact run-owned project ID, `target preview`, READY state, expected deployment ID/source, no Production alias, and effective protection. Stop on any mismatch. Only then use authenticated `vercel curl --deployment` for the synthetic fixture matrix. Retain raw target/build/trace/function evidence and separate Julusian and Sharp verdicts.
6. Retain the placeholder until the Preview is attested and the probe ends. Capture run-owned cleanup evidence, then remove only the exact two deployments/project (or the exact run-owned project with both deployments), and verify absence. Never delete a deployment from an unrelated project.

The generated deployment URL may exist even with `--skip-domain`; the protection check is required. A Production *classification* inside an inert, isolated project is distinct from LabOS Production deployment or traffic. The retry would create one run-owned Vercel project, one protected inert Production placeholder, one intended protected Preview probe deployment, and local run-owned source/evidence. It would not create a Git repository or touch the LabOS Vercel project. A deployment's target cannot be definitively attested before its upload/creation; it can be attested **before endpoint invocation**. Flags, dry runs, and branch names alone are insufficient. If the second deployment is again classified Production, stop without invoking it and preserve the raw response for Vercel support.
