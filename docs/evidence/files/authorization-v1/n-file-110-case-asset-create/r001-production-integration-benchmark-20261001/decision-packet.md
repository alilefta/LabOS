## Selected helper architecture recommendation

1. Own reviewed production C source under a new Files-native R001 location in the repository, separate from the retained `scripts/authorization/files/jpeg-r001/native-helper-feasibility.c` research probe. Keep direct `jpeg_mem_src`, custom fatal warning/error manager, `jpeg_start_decompress`, every scanline, zero-progress rejection, and `jpeg_finish_decompress`. The production source must add containment and lifecycle handling; the run-built feasibility executable is not promoted.
2. Pin the official libjpeg-turbo **3.2.0 VC x64 installer** at SHA-256 `662761d8ba8dae04aec74023ebaeceb856c2b56b9b59cfd180759d26300dda42`; verify Authenticode and extracted `jpeglib.h` SHA-256 `ea0fbba47e9e5da192a487df4df3cf01a338b86a0a85d154ef329dd7b5439043` and `jpeg-static.lib` SHA-256 `b9640752d84cfbac3efcce70096c3a586ab6ad95b1163541ba9a11446a3337cc` before building. Build with a checked-in deterministic VS 2022 x64 script (`/std:c11 /TC /W4 /WX /wd4324`), record compiler/linker versions and resulting binary hash in a build manifest. Static link the reviewed libjpeg library; the benchmark binary's only reported dependency was `KERNEL32.dll`. Any compiler/library/source change requires new hash, tests, and review.
3. For the currently evidenced `next start` layout, package the generated Windows x64 executable and its hash manifest in a fixed server-owned application directory (proposed `native/bin/win32-x64/r001-codec.exe`). Resolve an absolute path from a verified application root; never search `PATH`, accept a browser path, or fall back to Sharp. Restrict write permissions to the build/deployment owner. Check platform/architecture, file existence/hash, protocol version, and executable permissions at server startup and immediately before spawn; failure makes Case validation unavailable. A future standalone/container/serverless deployment must explicitly include and verify the binary in its output; Next's installed output-tracing docs do not make arbitrary executables part of the current build automatically. `serverExternalPackages` is not a substitute because the helper is an executable, not a Node package import.
4. One short-lived process handles one immutable original encoded byte buffer. Retain versioned `LJ01` framing as the candidate: binary stdin magic (4 bytes), little-endian unsigned length (4 bytes), exact bytes, EOF. The helper rejects empty, oversized, missing, extra, or truncated frames. It returns one bounded ASCII line (`LJ01 OK width height components completedScanlines` or a closed error code) and an exit status. Parent accepts success only for exact zero exit, empty stderr, one syntactically exact stdout line under 96 bytes, matching inspector dimensions/components and full height. Cap stdout/stderr capture, terminate on overflow, and never forward native diagnostic text or encoded bytes to application logs/client errors. No provider key/URL is sent to the child.
5. The Node adapter uses a hard monotonic wall timer, a small bounded semaphore/queue, and cancellation. On timeout/cancellation it closes IPC and terminates the child, waits for exit, and returns generic unavailable. The production Windows helper must establish an OS process-memory limit **before reading the JPEG** or fail closed if the limit cannot be installed. A Windows Job Object with process-memory limit is the proposed mechanism; the implementation must test behavior when an enclosing host Job Object prevents assignment. The helper must spawn no descendants. Parent shutdown/crash cleanup needs a tested parent-liveness channel or parent-owned Job Object: graceful `child.kill()` alone does not prove cleanup after abrupt parent death. This mechanism is a CODE/runtime gate, not something the benchmark helper demonstrated. No clinical temp file is proposed; the server holds at most one bounded original buffer per active validation and zeroes/drops references after disposition. Queue entries retain identifiers only, never byte buffers or public URLs.
6. Bundle the exact upstream `LICENSE.md` and `README.ijg` with deployment documentation. The extracted license says a statically linked libjpeg-API application must state that it is based in part on the work of the Independent JPEG Group; preserve upstream notices and have redistribution reviewed before shipping. The benchmark extracted license SHA-256 is `cff8701dc999e39b5044ece8f22ed65b3a10d6a8dbddca8ffb802d24580181db` and `README.ijg` SHA-256 is `db16a04128171879c60708d171b88d97345a2dd20f9bfc173680a4497c73f704`. The benchmark's `cjpeg` fixture tool is not part of the proposed application binary.

## Retrieval and exact-byte protocol recommendation

The Files/provider adapter takes only the server-resolved reserved `FileUploadGrant.providerFileKey` after fresh Case/tenant/Member/purpose/expiry checks. It calls installed UploadThing 7.7.4 `UTApi.getFileUrls(key, { keyType: 'fileKey' })`, requires exactly one result and byte-for-byte returned-key equality, and never accepts client/callback URL, MIME, filename, size, or provider hash as authority. Isolate this deprecated SDK method behind that adapter and track replacement on an SDK upgrade.

**Fail-closed URL policy pending the provider probe:** parse the returned URL; require HTTPS, no userinfo, approved port/origin and observed key/path relation. Reject fragments and unexpected query parameters unless a real probe establishes a necessary exact form. Allowlist provider-controlled origins from evidence, not an arbitrary `*.ufs.sh` wildcard. Reject redirects by default; if the real object requires one, separately approve a finite hop count with the same checks at every hop. To prevent DNS precheck/rebinding gaps, use an HTTPS client with a pinned result from a DNS lookup that rejects private, loopback, link-local, unspecified, multicast and other non-public addresses while retaining TLS hostname verification. A preliminary `dns.lookup` followed by an unrelated `fetch` is insufficient. The current `next.config.ts` enables full-URL fetch logging, so the proposed adapter must use a dedicated HTTPS client whose URL never enters that logger. Reject non-200 and partial responses, unexpected content encoding, and failed/incomplete streams. `Content-Length` is advisory: reject a declared over-limit early but count actual bytes, reject zero and limit+1, abort at the first excess byte, and accept an absent or false length only if the complete stream independently passes. Bound connection/read/wall time separately in the eventual provider runtime design. Never log URL/key, redirect target, request headers, or raw exception strings.

Accumulate at most 33,554,432 original bytes plus one detection byte in memory; copy once into the validation buffer, then feed **that same buffer** to SHA-256, R001 marker inspection, and the native frame. No transformed or second fetch is silently substituted. The checked result carries only grant/tenant/Case/key identity internally and measured profile, size, dimensions, suffix result, and SHA-256. Public-read retrieval is not private; possession of the URL bypasses LabOS authorization.

On first successful validation, hold the exact buffer/result while the existing finalization transaction locks and rechecks the live PENDING reserved grant, current Case/tenant/Member policy and expiry, inserts complete immutable evidence, and changes the grant to `UPLOADED` atomically. No evidence is written for failure. Because attachment is a separate later transaction and UploadThing immutability is unproved, **attachment must refetch the reserved key and require SHA-256 equality with evidence immediately before/within its authorized consume-and-attach transaction**; otherwise it fails closed and does not consume or attach. This proves equality at the check, not that a public object can never later change. Provider immutability or a later read-integrity strategy remains a runtime/security residual before durable byte-integrity claims. No provider MD5 substitutes for R001 SHA-256.

No real UploadThing object was created. The workflow excludes external development-provider mutations from standing authority; the Product Owner's conditional probe language did not expand it. Thus actual lookup URL, host/path/key form, redirects, headers, repeat-byte behavior, DNS answers, and cleanup are **NOT_RUN**. A separately authorized exact run-owned synthetic provider probe must precede freezing the host/path allowlist and activating this protocol.

## Recommended local Windows x64 containment policy — **not approved constants**

| Control | Recommendation | Basis and limitation |
| --- | --- | --- |
| Per-helper hard wall | **10 seconds** from spawn through close | About 2.9× the slowest observed four-way child; does not prove all accepted JPEGs fit. Timeout is operational fail-closed, not an R001 work score. |
| Per-helper process private-memory hard cap | **384 MiB** via tested Windows Job Object before reading bytes | About 2.28× the highest sampled 176 MB private bytes. Rebenchmark under real hosting job configuration and malformed high-memory inputs. Monitor working set separately; RSS is not the same quantity as private commit. |
| Active helpers | **2** per measured host | Two-way 50 MP group max 3.22 s and reserves memory for the 16 GB host/Next process. Four-way worked but showed higher tail and doubles possible reserved memory. |
| Waiting queue | **2 identifiers**, maximum **5 seconds** waiting; then generic fail-closed overload | Two active 50 MP cases finished within 3.22 s here; queue never owns provider bytes. These are capacity recommendations, not product acceptance. |
| Output/IPC | 33,554,432-byte frame input; stdout <96 bytes, stderr bounded and empty on success | R001 encoded ceiling and tested `LJ01` shape. Any extra/malformed output fails. |

At two active 384 MiB caps, the native reservation envelope is 768 MiB plus two bounded Node buffers and normal application memory. This is a planning envelope, not measured aggregate usage. The production implementation must test process-memory enforcement, timer cancellation, parent shutdown/crash, malformed IPC and queue overload; the feasibility helper lacks those features. A different OS, CPU, memory allocation, virtualized host, compiler, or libjpeg-turbo build requires a new build identity, representative benchmark, numeric recalibration and review before use.
