# N-FILE-110 checked-suffix handoff architecture decision

Status: **independent V3 `PASS | ARCHITECTURE/DECISION`**. Scope: design only. The preceding S001 finalization gate remains `BLOCKED_DECISION`; finalizer CODE, disposable PostgreSQL verification, and finalization review remain `NOT_RUN`. No application code, Prisma schema, SQL migration, grant, evidence row, provider object, or runtime route was changed here.

## Current problem and authority

`app/api/uploadthing/case-clinical-route.ts` receives one UploadThing middleware `files[0].name`, applies a case-insensitive terminal `.jpg`/`.jpeg` check, then invokes `stageCaseAsset({caseId})`. That staging command and its serializable writer receive no filename or suffix. The writer creates the canonical saved-DRAFT, `case.asset.add`-authorized, Case-targeted `N-FILE-110`/`case.asset.add.stage` PENDING `FileUploadGrant` for 15 minutes. The verified callback sends only the middleware-created grant ID and UploadThing object key to the Case callback repository, which reserves that key on the same live grant; its strict parser rejects extra callback fields. `resolveReservedClinicalGrant()` and the private S001 retained `{grant, original}` context have no suffix. The S001 byte core correctly proves JPEG bytes, not a filename suffix. Thus `CaseClinicalUploadEvidence.validatedSuffix` (`JPG | JPEG`, required) has no truthful source at finalization.

The installed evidence schema requires the canonical `providerObjectKey` for its grant/object identity and composite foreign key. That existing key remains; no additional key, URL, locator, filename, or provider metadata is proposed for evidence. Evidence's accepted suffix meaning is the **checked upload filename's terminal suffix**, not a label inferred from JPEG magic, MIME or decoder output.

## Decision: grant-owned bounded fact

**Chosen owner:** the existing `FileUploadGrant`, because it is created transactionally at the authorized upload-initiation boundary and already carries the exact tenant, Member, Case target, purpose, expiry and later callback-reserved provider key. There is no existing persisted bounded filename/suffix metadata field or separate authoritative reservation object. Carrying suffix in callback metadata would defer authority to another envelope and require a second persistence handoff; the verified callback needs only to bind the exact provider key to the already-qualified grant.

**Capture:** in the server-only UploadThing middleware/staging path, after the existing one-file, declared-MIME, size and terminal-suffix checks, normalize the terminal ASCII suffix with one shared parser. The final filename suffix match is case-insensitive: `.jpg`/`.JPG` → `JPG`; `.jpeg`/`.JpEg` → `JPEG`; missing/other suffix rejects. The parser uses only the final terminal suffix, never stores the raw filename, and returns the existing `CaseClinicalValidatedSuffix` bounded domain. The raw name is untrusted upload-initiation text. The authoritative fact is that LabOS checked and accepted that text for this exact upload initiation; it is **not** independent proof that the provider object has a particular filename or valid JPEG bytes. The route's strict `{caseId}` client input stays unchanged. No client-facing parameter accepts a pre-normalized suffix; a server-only stage path carries the parser result into the same grant-creation transaction, where it is bound to that grant ID and canonical target.

**Persistence:** propose nullable, no-default `FileUploadGrant.caseClinicalValidatedSuffix CaseClinicalValidatedSuffix?` (actual Prisma name to be reviewed at authoring) using the existing evidence enum. It is Case-only and written exactly once at grant insertion. Non-Case grants must keep it null. For new N-FILE-110 Case grants it is required at insertion and immutable thereafter, including across provider-key reservation, status changes and cleanup. A callback cannot set, clear, or switch `JPG ↔ JPEG`.

**Callback:** no suffix field is added to verified callback input or response. The Case repository loads the grant's already-stored suffix and requires it to be nonnull before accepting a key reservation or same-key replay. A callback-provided name, MIME, URL or suffix is never authoritative. The grant ID from server middleware metadata still correlates the verified provider event to the exact grant, and the existing key/tenant/Case/Member/expiry checks remain mandatory.

**Grant resolution and S001:** `resolveReservedClinicalGrant()` reads and requires the bounded grant suffix along with the existing PENDING, exact key, tenant/Member/Case/DRAFT/assignment and expiry checks. The outer `validateReservedClinicalJpegS001()` retains that grant snapshot privately with the exact original Buffer. `validateClinicalJpegS001Bytes()` remains unchanged and has no filename responsibility. Direct synthetic byte-core results retain no grant context and cannot later finalize. The finalizer must re-read the same grant transactionally, require the same suffix and all existing identity/authority facts, then copy `validatedSuffix` from the fresh authoritative grant row into evidence. The evidence insert trigger should independently require nonnull grant suffix and exact equality with `NEW.validatedSuffix`, in addition to its installed grant/key checks.

## Validation completion time

The accepted `CaseClinicalUploadEvidence.validatedAt` meaning is the server clock **after successful complete JPEG inspection**, not the later evidence-insert time. The outer validator should capture a server completion instant immediately after the production S001 byte core returns successfully and cancellation checks pass, then retain an immutable primitive timestamp (for example epoch milliseconds) in its private WeakMap context beside `{grant, original}`. The public/narrow byte-core result need not gain a timestamp, and a direct synthetic core call gains no finalizable context. The future finalizer reconstructs the Date from the private timestamp, verifies original length/SHA again, and checks it against fresh grant creation/expiry and transaction database time before inserting evidence. A delayed or expired finalization fails closed; it must not replace the original completion time with `now` merely to pass expiry. No re-decode is implied.

## Additive migration and cutover design — not authored

1. Add the nullable/no-default Case-only grant column of the existing `CaseClinicalValidatedSuffix` enum. Do not backfill or default historical nulls. Existing Catalog/WorkType/Product/Dentist grants retain null.
2. In one explicit PostgreSQL transaction, strengthen the existing `FileUploadGrant_case_identity_guard`: new Case-scope grant INSERT requires the suffix; UPDATE rejects any suffix change (`IS DISTINCT FROM`) for Case scope, while pre-existing null Case grants may retain null for expiry/cleanup. Add a two-valued scope CHECK so non-Case grants cannot carry the Case suffix. Do not make the shared column globally `NOT NULL`.
3. Strengthen the existing `CaseClinicalUploadEvidence_validate_grant` insert function to require the grant suffix nonnull and `NEW.validatedSuffix IS NOT DISTINCT FROM` that suffix. Existing immutable/deferred evidence triggers and composite grant/provider key FK remain installed. Historical evidence rows are neither updated nor rechecked by this insert-only trigger change.
4. The migration must preserve raw-SQL trigger definitions, use an explicit `BEGIN`/`COMMIT` for all-or-nothing DDL under the repository's Prisma/PostgreSQL execution pattern, and receive separate CODE/SQL, disposable PostgreSQL, and normal-development application gates. The new writer cannot create a Case grant until the column is installed; an old writer facing the new insert guard fails closed. N-FILE-110 route activation stays separate. No later global `NOT NULL` is needed while non-Case and historical rows must remain null.

**Historical behavior:** the last independently attested normal-development snapshot had two `FileUploadGrant` rows and zero clinical-evidence rows. A [read-only target-attested count](s001-checked-suffix-dev-readonly-inventory-20261004.json) on 2026-10-04 found those two grants were non-Case `N-FILE-102`/Catalog `UPLOADED` and expired; it found **zero Case grants and zero evidence rows**. The read-only transaction was rolled back. This is a point-in-time observation, not a substitute for migration preflight. In other environments, any pre-change Case grant necessarily has null suffix: a PENDING one is ineligible for callback reservation, S001 grant resolution and evidence finalization after cutover. It must expire or follow separately authorized cleanup; a fresh authorized stage **and new upload** is required, rather than backfilling or reusing a reserved key. Historical terminal grants retain their status/records and null suffix; any pre-existing valid evidence remains immutable and untouched. The new evidence insert equality guard applies only to new rows. Rollback of an unapplied candidate is source revert; after installation, dropping the column/guards would remove provenance protection and needs a separately reviewed rollback migration, never an implicit fallback to inferred `JPG`.

## Security and compatibility tests for the successor

- Parser/route: `.jpg`, `.jpeg`, mixed-case variants normalize to the exact enum; missing or non-JPEG terminal suffix, invalid size/MIME/file count reject before grant creation; no arbitrary raw filename persists. An earlier dot in a filename does not change the accepted terminal-suffix rule.
- Grant creation: normalized suffix is inserted with the authorized exact Case/tenant/Member/purpose/grant; new Case grant missing suffix rejects; non-Case grant with suffix rejects; existing null grants and old evidence survive migration unchanged.
- Immutability: SQL and application attempts to switch `JPG ↔ JPEG`, clear it, or set it later on a historical null grant reject. Callback metadata with suffix/name rejects; provider metadata cannot override the stored suffix. Same-key callback replay may acknowledge only a live grant and cannot change suffix.
- Resolver/finalization handoff: null historical suffix, wrong grant, changed target/tenant/assignment, stale/expired grant or suffix mismatch fails closed before provider use or evidence insert. Private retained context carries original grant suffix and completion time; fresh transaction rechecks both. Direct S001 byte-core result cannot finalize.
- Evidence: finalization writes exactly the grant's checked enum value and canonical required `providerObjectKey`, with no URL, duplicate key, filename or diagnostic. Evidence insert with a different suffix fails at the actual trigger. Successful evidence plus `PENDING → UPLOADED` remains atomic under existing deferred triggers; failure/concurrency leaves no partial success. `validatedAt` is the retained successful-inspection completion instant, not finalization time.
- Migration runtime: representative historical null Case grants and unrelated grants preserved, new Case insertion required, non-Case isolation, insert/UPDATE guards, evidence-suffix equality, transaction failure rollback, Prisma reconciliation, and exact cleanup in a fresh disposable PostgreSQL target.
