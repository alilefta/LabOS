## Observed provider facts

Three repeated `UTApi.getFileUrls(key, { keyType: "fileKey" })` calls each returned exactly one row whose returned key equaled the persisted run key. All three URL values were equal in memory (same SHA-256 prefix `bcdb4e230256`). The observed URL was HTTPS, exact origin `https://fyylnhrlmu.ufs.sh`, default HTTPS port, no userinfo, query, or fragment, with path shape `/f/{exact-provider-key}`. The hostname equaled `{development-token-appId}.ufs.sh` for this app. These are observations of one app/object, not a claim about every UploadThing app or future SDK.

DNS lookup on each attempt returned public IPv4 addresses `188.114.96.7` and `188.114.97.7`. The probe pinned the selected `188.114.96.7` into the HTTPS connection after checking the answers and kept TLS verification against the hostname. These addresses are observations, not a permanent IP allowlist. The request used `Accept-Encoding: identity` and did not follow redirects.

All three GETs returned initial status **200**, no `Location` and no `Content-Encoding`. Each had `Content-Length: 286`, `Content-Type: image/jpeg`, `Cache-Control: public, max-age=86400`, `Accept-Ranges: bytes`, an ETag (identical fingerprint across attempts), and no `Last-Modified`. The actually streamed byte count was 286 each time; each independently computed SHA-256 equaled the local source. `Content-Length`, content type, and ETag were recorded as provider metadata, not JPEG or object-identity authority. The three equal fetches do not prove future object immutability. Raw sanitized lookup/DNS/header/byte observations are in [probe-results.json](probe-results.json).

## Proposed narrow production retrieval policy

This policy is proposed for the currently attested UploadThing app and installed SDK, subject to independent review and the later production CODE gate:

1. Take only the server-persisted reserved `providerFileKey`. Call `UTApi.getFileUrls(key, { keyType: "fileKey" })` inside the Files/provider adapter. Require exactly one row and byte-for-byte returned-key equality. Keep the deprecated SDK method isolated and track its replacement for SDK upgrade.
2. Require URL parse success; `https:`; no username/password; no explicit non-default port; no fragment; no query for the observed V1 form; and exact path `/f/${encodeURIComponent(key)}` (or reject if the key's encoded form differs from the observed safe ASCII form). Require exact origin `https://fyylnhrlmu.ufs.sh` for the currently attested development app, additionally checking its hostname against the decoded attested app ID. An alternate app/origin/path/query requires fresh provider evidence and reviewed configuration, not a wildcard fallback. Do not allow arbitrary `*.ufs.sh`, `utfs.io`, callback URL, or client URL as retrieval authority.
3. Resolve the approved hostname for each request. Reject any DNS answer that is non-public, including private, loopback, link-local, unspecified, multicast, reserved and mapped forms. Connect to a vetted resolved address by a transport mechanism that pins that address into the actual socket, while retaining URL-hostname TLS certificate/SNI verification. Do not perform a standalone DNS precheck followed by a second unpinned resolution. Reject proxy behavior or runtime transport settings that bypass this pinning. A production implementation needs exhaustive address-class tests; the probe's compact IP check is evidence tooling, not the production validator.
4. Disable redirects. Require a single complete `200` response; reject 3xx, partial `206`, non-200, network interruption, and truncation. Request identity encoding and reject any present non-identity `Content-Encoding`. Treat `Content-Length` as advisory: reject an announced value over 33,554,432 early, but still count actual streamed encoded bytes and abort at byte **33,554,433**, including when length is missing, false, or shorter than actual. A declared length mismatch is a rejection. Bound network time and buffering under the separately implemented production resource policy. Keep one bounded original encoded buffer for R001/SHA/finalization; no transformed copy or provider hash substitution.
5. Suppress the key, full URL, URL query, response bodies, and provider errors containing them from logs, telemetry, client errors, audit descriptions, and unrelated DTOs. The public URL remains a bearer retrieval path; minimizing it does not provide confidentiality.
6. Preserve the approved exact-byte lifecycle: R001 and SHA-256 consume the same immutable retrieved bytes; successful clinical evidence and `PENDING → UPLOADED` occur atomically in the later authorized finalization transaction while that result is retained. At separately authorized attachment, refetch the reserved key and require SHA-256 equality with immutable evidence before consume/attach. This checks equality at the two moments; it does not establish permanent UploadThing object immutability.

## Cleanup and limits

`UTApi.deleteFiles(exactRunKey, { keyType: "fileKey" })` returned without throwing. The executed script did **not** inspect UploadThing 7.7.4's `{ success, deletedCount }` response; its `deleteAcknowledged: true` field in the retained [raw cleanup output](cleanup.json) is unsupported and must not be used as evidence of provider acknowledgement. The corrected [cleanup assessment](cleanup-assessment.json) records those response fields as `NOT_RUN`/not captured. An independent `listFiles({limit:100})` observation went from 25 objects including the exact key and run filename to 24 objects with neither. A fresh `getFileUrls` lookup then returned zero rows. See [post-delete-lookup.json](post-delete-lookup.json). These observations verify exact run-owned cleanup without relying on the unchecked deletion response. No unrelated key was targeted by the script. Post-deletion direct HTTP retrieval was `NOT_RUN`. The run-private temp manifest and scripts were removed after evidence retention; the retained evidence contains no credential, raw provider key, or full public URL.

One 286-byte object cannot establish all provider destinations, long-term byte immutability, behavior at the 32 MiB boundary, false/missing `Content-Length`, error response shapes, DNS changes, or a production HTTP client's SSRF resistance. Job Object enforcement, parent-crash cleanup, integrated R001 validation/finalization, and Case route activation remain `NOT_RUN` and separate gates. No production/staging provider was contacted.

The independent Reviewer initially returned `CORRECTION_REQUIRED` because the retained cleanup script/output inferred provider deletion acknowledgement without checking the SDK's `success` and `deletedCount`. The bounded correction above preserves the raw output, marks those response fields uncaptured, and attributes cleanup only to the exact-key/name read-back and zero-row lookup. The independent rereview returned **PASS | RUNTIME_EVIDENCE + ARCHITECTURE**. The Reviewer distinguished observed facts from proposed policy and did not perform provider operations.
