## Installed boundary and exact additive candidate

`CaseClinicalUploadEvidence` is a successful-only, one-to-one grant row. It already contains canonical Case/tenant/grant/provider-object identity, validated suffix/format, encoded length, authoritative dimensions, exact-original-byte SHA-256, `validationProfile`, and `validatedAt`. Its existing `BEFORE UPDATE OR DELETE` trigger makes the whole row immutable. Its insert trigger requires a live, target-bound `PENDING` N-FILE-110 grant; deferred triggers require evidence and `UPLOADED` to finalize together. There is no separate failure evidence row. Existing `validationProfile` is a bounded string shape, not an S001 implementation identity.

Candidate source: [`prisma/schema.prisma`](../../../../../prisma/schema.prisma) and [`prisma/migrations/20261002120000_case_s001_evidence_identity/migration.sql`](../../../../../prisma/migrations/20261002120000_case_s001_evidence_identity/migration.sql). The SQL creates enum `CaseClinicalCodecBackend` with sole value `JULUSIAN_TURBOJPEG` and seven nullable/no-default columns on `CaseClinicalUploadEvidence`: `validatorVersion` `varchar(48)`, `codecBackend` enum, `codecPackageVersion` `varchar(24)`, `codecLibraryVersion` `varchar(24)`, `codecRuntimeSha256` `varchar(64)`, `sourceComponents` integer, `isProgressive` boolean. No table or existing column is rewritten. The existing immutability trigger covers all seven automatically.

The new validated CHECK permits exactly two shapes:

1. `validationProfile = JPEG_CLINICAL_V1_S001`: all seven identity/source fields are required; version `LABOS_S001_JULUSIAN_V1`, backend `JULUSIAN_TURBOJPEG`, package `3.0.1`, library release `3.1.3`, lowercase 64-hex deployed-library SHA-256, source components 1 or 3, and non-null progressive fact.
2. Every other historical/current profile: all seven fields are null. Existing R001 evidence is neither labeled S001 nor backfilled with an invented codec identity. A future R001 identity extension needs its own reviewed candidate.

SQL uses two-valued predicates (`IS NOT DISTINCT FROM`, `COALESCE`) within the CHECK so a missing S001 field cannot pass PostgreSQL's null-valued CHECK semantics. The profile and evidence outcome remain the existing immutable `validationProfile` and successful-row presence. No provider key/URL, diagnostics, JSON, filesystem path, payload, or free-form text is added. `codecLibraryVersion=3.1.3` records the version declared by the reviewed Julusian 3.0.1 build; it is **not** by itself proof of which shared library loaded. `codecRuntimeSha256` must be computed/verified against the adjacent deployed `libturbojpeg.so.0` and a reviewed build manifest at cold start before S001 validation. The exact runtime digest was not established by the Preview experiment; no literal digest is invented in this design. This is a mandatory later CODE/build-identity acceptance condition.

### Migration, preflight, and rollback

Before any separately authorized application, attest target/history/checksums, verify the accepted preceding migrations remain unchanged, and read-only count any pre-existing `JPEG_CLINICAL_V1_S001` evidence. A nonzero count requires investigation; do not silently classify or backfill it. Apply only the pinned migration through the repository's canonical-LF Prisma migration procedure after separate disposable runtime and normal-development gates. The new enum/table columns/check are transactional PostgreSQL DDL; a failed transaction rolls back together. Historical rows acquire null fields only. The CHECK validates all existing rows on installation; it never treats null as S001. Existing legacy, R001, C2/C3, Catalog, WorkType, Product, and Dentist rows/structures are untouched.

Rollback before any S001 row can remove the CHECK, columns, then enum through a separately reviewed reversal. Once S001 evidence exists, dropping fields would destroy immutable provenance and is **not** an acceptable routine rollback. Forward recovery must retain evidence and deploy a compatible reader/validator, or disable new validation while preserving existing rows. A future backend/profile/version change requires a new allowlisted constraint/enum evolution and a distinct implementation identity; never overwrite an old row.

## Production-facing validator contract (design only)

Server-only input is an identifier for a persisted reserved Case grant, plus optional cancellation signal; it does not accept caller-supplied provider key, URL, tenant or validation profile. Resolve the grant and transaction-fresh Case/tenant/Member/assignment authority before provider access using the accepted N-FILE-110 grant resolver. After authorization, synchronously acquire a process-local admission token **before** exact-key provider lookup and large-byte retention. One token per function instance; if occupied, reject immediately with a generic unavailable/overload result. No application queue, buffered JPEG, key or URL may wait for a token. Release in `finally` on every async exit. This gate is per instance, not global across Vercel instances. A process crash terminates its token with the instance; no cross-instance lease is claimed.

Use the accepted server-only UploadThing exact-key adapter and URL/DNS/TLS/HTTP/streaming limits unchanged: persisted reserved `providerFileKey` → exact returned-key equality → reviewed origin/path and pinned public DNS/TLS connection → complete bounded 200 identity response → one original `Buffer` of at most 33,554,432 bytes. No callback/client URL or provider metadata establishes byte authority. Run the accepted unchanged structural inspector first, hash the same `Buffer`, then invoke **only** pinned Julusian `decompressSync` for complete pixel output (gray for source 1-component, RGB for source 3-component). Reject load/decode failure, dimension mismatch, output length mismatch, or post-decode original-buffer SHA mismatch. The inspector alone owns source dimensions/components/progressive/marker facts; decoder output never overrides them. No Sharp, R001 impersonation, alternative decoder or automatic downgrade.

Return an internal immutable `ValidatedClinicalJpegS001` with profile, exact encoded length/SHA, inspector width/height/components/progressive, version/backend/package/library/runtime-digest identity, and server-resolved grant context. Retain the exact original buffer through a private server-only association for the separately authorized immediate finalization lifecycle; expose neither buffer, key nor URL in a client DTO. A later finalizer must assert retained-buffer length/hash and transaction-fresh authorization/grant/Case/expiry/key state, then insert immutable successful evidence and update `PENDING → UPLOADED` atomically under existing deferred constraints. The finalizer is **not implemented or authorized here**. A later attachment must independently refetch the exact reserved key and require SHA equality with immutable evidence before consuming/attaching. Provider MD5 is never substituted.

### Vercel operational configuration and limitations

Use a Node.js function, not Edge, with an explicit reviewed Node/N-API and Linux x64 deployment identity. Pin Julusian 3.0.1 in production dependencies and lockfile. The accepted Preview required native addon and adjacent `libturbojpeg.so.0` inclusion; the later implementation must externalize/trace both, verify actual deployed paths/hashes/loadability on cold start, and fail closed if absent or mismatched. Configure the specific validation function with `maxDuration: 30` only after confirming the deployed route/function supports that setting; do not set a global app duration. Record the selected Hobby 2-GB function envelope as an environment property, not a per-image allocation or hard native-memory cap. No Windows Job Object values carry over.

The 30-second function ceiling is not a promise that a JavaScript timer interrupts synchronous native decode. The accepted one-active/zero-waiter gate limits only local overlap. Vercel can run other instances concurrently, and an instance can still terminate from native crash/OOM. The 379.14-MiB RSS and 687.47-ms decode observations are synthetic samples, not upper bounds. The later CODE gate must test saturation and admission release, native load failure, deployment tracing, generic errors/no telemetry leakage, selected Vercel memory/duration settings, and byte-integrity checks. Real UploadThing retrieval, clinical flow, valid 128-scan and exactly-33,554,432-byte complete decoding, exhaustive malformed behavior, production deployment and same-instance parallel safety remain `NOT_RUN` or accepted limitations as recorded by the Product Owner.
