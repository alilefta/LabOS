## Proposed guarantee boundary — decision required, not approved

| Property | Accepted `JPEG_CLINICAL_V1_R001` STRICT | Candidate `JPEG_CLINICAL_V1_S001` STANDARD |
| --- | --- | --- |
| Original bytes | One immutable encoded sequence is hashed, structurally inspected, and directly decoded | The same original-byte and SHA-256 invariant is proposed |
| Structure and limits | Accepted R001 marker rules and numerical ceilings | Reuse the accepted inspector and applicable current JPEG limits, including exact terminal EOI and no trailing/concatenated content |
| Codec proof | Direct libjpeg-turbo/libjpeg API, custom fatal warning/error manager, start, every scanline, full finish | Complete decode through one explicitly approved higher-level decoder; decoder failure rejects; direct libjpeg calls and warning-fatal equivalence are **not** claimed |
| Result | Immutable R001 profile identity | A distinct S001 identity and actual backend/package/codec version; never record S001 as R001 |
| Availability | Accepted isolated Windows x64 helper only today | No accepted backend today; Julusian and Sharp are candidates |

Proposed S001 contract: require the server-authoritative exact provider bytes; apply the accepted structural inspector before decode; enforce the same encoded size, dimensions, pixels, metadata, segment, and scan ceilings; hash the exact bytes; force full decode of those bytes; cross-check decoded dimensions/components with the inspector; reject any reported decoder failure; record `JPEG_CLINICAL_V1_S001` and the actual backend/version immutably when a later persistence design is approved. S001 cannot promise that every codec warning is fatal unless the selected backend demonstrably exposes and rejects those warnings. The Product Owner must decide whether that weaker warning guarantee is acceptable. A silent R001→S001 downgrade, a decoder fallback, or a `DISABLED` mode that accepts files is forbidden. `DISABLED` means validation unavailable and attachment fails closed.

The current `CaseClinicalUploadEvidence.validationProfile` is an immutable required string, but the installed schema has no dedicated immutable backend/version fields. A later finalization design must establish truthful immutable backend/version persistence (including any additive migration) before S001 evidence can be written. It must retain the accepted exact-byte/SHA binding and later re-fetch equality check. This investigation makes no schema change.

## Julusian source and package findings

Verified against [`@julusian/jpeg-turbo` 3.0.1 package source](https://github.com/Julusian/node-jpeg-turbo/blob/v3.0.1/package.json), [CMake build](https://github.com/Julusian/node-jpeg-turbo/blob/v3.0.1/CMakeLists.txt), [decompress implementation](https://github.com/Julusian/node-jpeg-turbo/blob/v3.0.1/src/decompress.cc), [published Linux x64 files](https://app.unpkg.com/@julusian/jpeg-turbo@3.0.1/files/prebuilds/jpeg-turbo-linux-x64), and [releases](https://github.com/Julusian/node-jpeg-turbo/releases):

- Version 3.0.1 was released in January 2026. The package requires Node >=22.18, uses Node-API v10 and `node-addon-api`, and verifies a prebuild or compiles with `cmake-js`. This shows recent maintenance, not an operational support guarantee.
- Its CMake source pins a **libjpeg-turbo 3.1.3** source tarball (SHA-256 `075920b826834ac4ddf97661cc73491047855859affd671d52079c6867c1c6c0`), distinct from the accepted Windows R001 libjpeg-turbo 3.2.0 artifact. The published Linux x64 prebuild includes `node-napi-v10.node` and `libturbojpeg.so.0`; CMake sets `$ORIGIN` runtime lookup. The prebuilt's minimum glibc and actual Vercel loadability require runtime evidence.
- `decompressSync` performs TurboJPEG `tjInitDecompress`, `tjDecompressHeader`, and `tjDecompress2` with `TJFLAG_FASTDCT`, then destroys the handle. The async API uses a `Napi::AsyncWorker` in the libuv worker pool. Neither path calls traditional `jpeg_start_decompress`/scanline/finish APIs or sets `TJFLAG_STOPONWARNING`. A nonfatal warning may therefore be invisible to the caller; actual warning-corpus behavior remains to be measured. It cannot claim R001 as published.
- It allocates decoded output based on header dimensions and pixel format (1/3/4 output bytes per pixel) and also holds input/native decoder allocations. The accepted structural bounds should run first, but the addon is in the long-lived Node process. Synchronous use blocks the event loop; async use occupies a libuv worker and does not itself provide hard per-decode termination or memory isolation.

**Architectural conclusion:** Julusian is the first S001 feasibility candidate because its API is narrow and JPEG-specific and its Linux x64 prebuild is published. Its warning policy and Vercel load/decode behavior must be established before S001 approval. A general-purpose traditional-libjpeg strict decode primitive could fit the project's small native API, but upstream acceptance, maintenance, version pinning, error-manager design, and platform packaging are hypotheses. A contribution must expose general codec semantics, never LabOS/R001 policy or ceilings.

## Sharp findings

The repository lockfile contains transitive `sharp@0.35.4` and Linux x64 platform packages; `package.json` does not declare Sharp or Julusian as a direct validation dependency. Sharp [installation guidance](https://sharp.pixelplumbing.com/install/) documents Node-API v9 prebuilds for Linux x64 glibc >=2.28 and platform-specific optional packages. [Metadata](https://sharp.pixelplumbing.com/api-input/) reads headers without full pixel decode. To force full evaluation, the candidate operation is a pixel-producing pipeline such as `sharp(originalBytes, { failOn: 'warning', limitInputPixels: 50_000_000 }).raw().toBuffer({ resolveWithObject: true })`, followed by dimensions/channel checks. This allocates a full output buffer and may involve colorspace conversion; it is not the R001 direct-libjpeg proof. Sharp [constructor options](https://sharp.pixelplumbing.com/api-constructor/) document `failOn` behavior; [output API](https://sharp.pixelplumbing.com/api-output/) documents raw output. Versioned [native source](https://github.com/lovell/sharp/blob/v0.35.4/src/pipeline.cc) routes JPEG buffer input through libvips JPEG loading; execution is lazy until output is requested. Corpus evidence must establish how its warning/error behavior works for the proposed S001 contract. Sharp is a plausible alternate S001 backend with a well established Next/Vercel packaging path, but broader image processing, full raw allocation, and process-native failure surface require separate resource evidence.

| Strict libjpeg-turbo WASM | Hypothetical | Requires exact warning/error/scanline semantics, codec identity and independent proof | Potential worker/linear-memory containment; performance and Vercel packaging unmeasured |
| Future Linux Docker/VPS isolated helper | Hypothetical | Closest path to current process-isolated R001 architecture | Needs Linux build, process/memory/kill-tree policy, benchmark and review |
| `DISABLED` | No acceptance | No acceptance | Fail closed; never bypass codec validation |

The Windows 10-second/384-MiB/two-active/two-waiting/five-second policy cannot be transplanted to Vercel without target-specific evidence. In-process addons can crash or exhaust a whole function, and a Node cancellation does not establish interruption of native decode. Sharp's cache/concurrency settings and Vercel function limits are not a per-JPEG hard cap. Separate process or worker containment on Vercel is unproven.

## Vercel feasibility and packaging

[Vercel Node.js functions](https://vercel.com/docs/functions/runtimes/node-js) provide Node APIs, and [supported Node versions](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions) include current Node 24.x and 22.x; Julusian's Node >=22.18 requirement is plausible. This does not attest the actual LabOS Preview OS/architecture/libc, Vercel settings, native module loading, resource envelope, or deploy bundle. The current `next.config.ts` contains no validation-specific native tracing/externalization rule. [Next output file tracing includes](https://nextjs.org/docs/app/api-reference/config/next-config-js/output) can include an exact `.node` and adjacent `.so` in the relevant server function; [serverExternalPackages](https://nextjs.org/docs/app/api-reference/config/next-config-js/serverExternalPackages) may be needed for a native addon. Sharp is on Next's documented automatic externalization list, but its platform package still needs inclusion verification. [Vercel's tracing guidance](https://vercel.com/kb/guide/how-can-i-use-files-in-serverless-functions) supports route-specific traced files. No deployment or function execution was performed here. Preview must record actual platform, Node/N-API/glibc, traced files, cold/warm load, and full decode.

## Differential and conformance experiment

Use the accepted Windows R001 implementation as a **reference oracle**, not as proof that another backend is equivalent. Feed identical synthetic original encoded bytes through structural inspection, SHA-256, Windows R001, and each candidate full decoder. Include valid baseline RGB, progressive RGB and grayscale; every exact numerical boundary and limit+1; high accepted metadata/segments/scans; malformed markers, unsupported coding/precision, truncation, entropy corruption, missing/premature EOI, trailing bytes, concatenated JPEG, decoder warnings, and decoder-specific edge cases. Record raw encoded hash, dimensions/components, structure outcome, codec outcome/warning/error, versions, time, memory, and platform. Compare disagreement categories explicitly.

Passing the proposed S001 corpus and real Preview execution would support **S001 conformance**. Agreement with R001 on a finite corpus is only **differential evidence**. An R001 backend claim additionally requires source-level proof of the accepted direct-libjpeg API sequence, fatal warnings/errors, full scanline and finish behavior, same-byte integrity, pinned codec identity, containment, and independent review. Do not infer strict equivalence from image appearance or successful decode.
