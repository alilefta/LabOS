# Proposed JPEG_CLINICAL_V1_S001 contract and Vercel Julusian gate

Status: **proposed; Product Owner production approval pending**. This packet does not change the accepted `JPEG_CLINICAL_V1_R001`, its Windows x64 `PASS | CODE`, or the `PO HOLD / DEFERRED` clinical-finalization gate. The selected V1 S001 backend candidate is `@julusian/jpeg-turbo@3.0.1`; Sharp retains its Preview-feasibility `PASS` as an unselected alternate and is not a fallback.

## Exact proposed acceptance rule

One bounded original encoded `Buffer` is the sole input to length enforcement, the existing authoritative `inspectR001` structural inspector, SHA-256, and Julusian full decode. The name `inspectR001` is an implementation name: its current structural rules are shared unchanged for this proposed S001 release, without copying or forking the parser. Reject zero bytes and length above **33,554,432**. The inspector must pass its existing 8-bit Huffman baseline/progressive, one/three-component, terminal EOI/no trailing or concatenated bytes, and marker validity rules, plus width/height **≤9,000**, pixels **≤50,000,000**, APP0–APP15+COM payload **≤262,144**, length-bearing segments **≤512**, and progressive SOS **≤128**. Each equality boundary passes the structural layer if otherwise valid; limit+1 rejects.

Compute SHA-256 over the exact original bytes. Invoke the pinned Julusian/TurboJPEG backend on those same bytes and force complete pixel output; any load, allocation, decode, timeout, or result-contract failure rejects with a generic unavailable result. Check decoded width/height against the inspector and output length against expected width×height×chosen output channels. Never let decoded dimensions, output channels, callback metadata, file suffix, or provider MIME override source structural facts. The inspector owns source components, progressive status, metadata/segment/scan counts, and exact EOI exhaustion. The codec owns the weaker S001 complete higher-level decode proof. No Sharp fallback, skipped decode, or automatic R001→S001 downgrade is permitted. Disabled backend means validation unavailable and fail closed.

`JPEG_CLINICAL_V1_R001` additionally requires its accepted traditional libjpeg API lifecycle: fatal warnings/errors, successful start, every scanline read with zero-progress rejection, full output height, and successful finish. The published Julusian 3.0.1 TurboJPEG API does not prove that lifecycle or fatal-warning equivalence. **An S001 success is never an R001 success**, even on identical corpus outcomes.

## Narrow result and future immutable evidence identity

The isolated experiment may return only profile `JPEG_CLINICAL_V1_S001`, exact encoded length/SHA-256, inspector-established width, height, source components and progressive flag, bounded structural counts, selected backend identity, decoder completion result, and bounded timing/resource observations. It creates no Case or clinical evidence.

The installed `CaseClinicalUploadEvidence` has immutable `validationProfile`, `measuredSizeBytes`, `width`, `height`, `contentSha256`, `validatedAt`, and Case/grant/provider identity. Its existing SQL trigger rejects UPDATE/DELETE; its profile-shape check permits the proposed S001 name but does not itself approve that profile. The row can truthfully store the profile and some measured facts but **cannot explicitly store backend family, exact application validator version, pinned package version, embedded/runtime codec identity, source components, or progressive status**. A later authorized finalization design requires an additive, immutable, allowlisted backend/version identity. Proposed narrow columns are `validatorVersion`, `codecBackend`, `codecPackageVersion`, `codecLibraryVersion`, `codecBinarySha256` (only if measured against the deployed shared library), `sourceComponents`, and `isProgressive`, all nullable for historical rows with no default and populated together for future S001 success according to a reviewed constraint. The existing successful-only evidence row represents outcome by its presence; failed validation produces no success row. `validationProfile` stays the canonical immutable release identity; no arbitrary JSON, raw URL/key, diagnostics, or unbounded text is needed. Exact column types, allowed values, constraints, trigger compatibility, rollback, and historical-row semantics require separate CODE/SQL approval before a migration. This task authors no schema change or migration.

`@julusian/jpeg-turbo@3.0.1` is the selected backend candidate. Its source/build declaration pins libjpeg-turbo 3.1.3; the Preview feasibility probe observed a deployed Linux x64 addon with adjacent `libturbojpeg.so.0` but did not independently hash the runtime shared library against an upstream build. The future evidence identity must record a deterministically established runtime binary/build identity or an explicitly reviewed release identity; it must not invent certainty from the filename alone. A relevant package/embedded codec upgrade or backend switch needs conformance review and a new evidence identity before reuse of the S001 claim.

## Containment hypothesis for experiment

The accepted 33,554,432-byte input and 50,000,000-pixel limits imply up to **150,000,000 output bytes** for RGB or **50,000,000** for grayscale, before input buffers, Node/Buffer ownership, native allocations, and process overhead. Julusian runs in the Vercel Node process, so its allocation/crash surface is the whole function instance; a JavaScript timer cannot be claimed as a hard interruption of a synchronous native decode. The earlier 80.23–93.39 MiB tiny-fixture RSS is only baseline evidence. The isolated Preview experiment will measure representative larger inputs, timing, process RSS and bounded concurrency. These measurements support a later Vercel-specific policy proposal, not a proven hard per-JPEG memory wall. Production admission/concurrency, overload handling, wall behavior and deployment memory settings require a separately approved policy before S001 integration.
