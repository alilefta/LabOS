# N-FILE-110 rejected/orphan object cleanup — architecture decision

Status: accepted after independent V3 `PASS | ARCHITECTURE/DECISION` review. Design only; no provider or database operation was performed. The accepted S001 finalization and first-attachment checkpoints remain unchanged, and N-FILE-110 remains inactive. Actual provider deletion remains gated by the explicit provider capability prerequisite below.

## Installed facts and decision boundary

- `FileUploadGrant` has `PENDING`, `UPLOADED`, `CONSUMED`, `EXPIRED`, `FAILED`, `CLEANED`; an immutable Case target/provider key/checked suffix; `expiresAt`, `uploadedAt`, `consumedAt`, `expiredAt`, `failedAt`, `providerDeletedAt`, `cleanupAttemptCount`, `lastCleanupAttemptAt`, and `cleanupFailureCode`. The generic expiry writer can move `PENDING` or `UPLOADED` to `EXPIRED`. No Case cleanup writer exists. The current Case identity trigger does **not** enforce terminal status transitions or cleanup acknowledgment semantics.
- A verified Case callback can bind one exact UploadThing key while the grant is `PENDING`; the callback's failure is not itself a durable `FAILED` grant transition. If no key was reserved, LabOS has no exact-object deletion authority. The generic grant completion path carries a URL and is not the Case finalizer.
- S001 finalization inserts immutable `CaseClinicalUploadEvidence` and changes the exact grant `PENDING → UPLOADED` in one transaction. The installed evidence insert/deferred triggers require the grant to finish that transaction `UPLOADED`; they do not prohibit a **later** `UPLOADED → EXPIRED`. Evidence is append-only and its composite FK keeps the exact grant/provider key. Do not delete or rewrite it during cleanup.
- First attachment accepts only live `UPLOADED` plus exact evidence, no `StoredFile`, and current Case/creator authority. It locks the grant in its write transaction and atomically creates `StoredFile`, asset, version/current pointer and `CONSUMED`. `StoredFile.sourceUploadGrantId` and `(provider, providerObjectKey)` are unique. A canonical attached object is not an orphan.
- The installed UploadThing 7.7.4 `UTApi.deleteFiles(key, { keyType: 'fileKey' })` requests `/v6/deleteFiles` and returns `{ success, deletedCount }`; `getFileUrls(key, { keyType: 'fileKey' })` returns keyed entries, but is marked deprecated. Neither local API type proves deletion is immediately durable or that a timeout means failure. Current official [UTApi documentation](https://docs.uploadthing.com/api-reference/ut-api) supports exact-key deletion and describes `getFileUrls` as deprecated. Provider absence/confirmation behavior needs synthetic runtime verification before activation.

## Decision: terminalize, then delete, then acknowledge

The **Files server lifecycle worker** owns Case rejected/orphan cleanup. It selects only persisted N-FILE-110 grants, never a client URL, callback metadata, filename, Case ID, provider listing/prefix, or guessed key. A scheduler may invoke it later; neither the callback, S001 validator, finalizer, nor attachment writer synchronously deletes a provider object. Application errors remain generic.

An object becomes deletion-eligible only after a database transaction has irreversibly ended its path to attachment and established that no `StoredFile` exists for either its grant or `(UPLOADTHING, providerFileKey)`. Two terminal reasons are allowed: a **definitive** rejected/failed `PENDING` reservation becomes `FAILED` with `failedAt` and bounded `failureCode`, or database time reaches `expiresAt` and a `PENDING` or unattached `UPLOADED` grant becomes `EXPIRED` with `expiredAt`. Transient provider/validation errors while the grant remains live do not by themselves end retry eligibility. `UPLOADED` plus evidence and no file remains retryable until expiry; after expiry it is never attachable again. `CONSUMED`, any grant with a `StoredFile` or version, and all inconsistent/ambiguous states are ineligible for this cleanup path. **Actual provider deletion remains blocked by a capability prerequisite:** UploadThing must authoritatively establish that the reserved file key cannot be rebound to a different object and that the exact-key absence query is an authoritative confirmation. A synthetic probe alone cannot prove those enduring properties. If UploadThing cannot provide them, this design must return for a provider immutable-version/ownership mechanism; do not activate deletion with key-only evidence.

The terminal transition and all cleanup claims lock the exact grant row and check: `boundaryId = N-FILE-110`, purpose `case.asset.add.stage`, Case target, provider `UPLOADTHING`, exact nonempty persisted key, null provider URL, null `consumedAt`, null `providerDeletedAt`, no `StoredFile` by source grant **or** provider/key, and no Case version through either file. For `UPLOADED` expiry require its exact immutable evidence and grant/evidence tenant, Case, key and suffix agreement; a missing/mismatched evidence row is inconsistent, not license to delete. A `PENDING` key-bearing grant must have no successful evidence. A terminal `FAILED` or `EXPIRED` retry is eligible only if these same checks still hold. The original key and checked suffix stay stored for audit/provenance; no new provider URL is stored. Keyless terminal grants cannot drive exact deletion and remain terminal for separate reconciliation.

The Case-only SQL guard and every terminalization/claim predicate must also enforce this complete marker matrix. A row outside it is quarantined from cleanup, not normalized opportunistically:

| Status | Required markers and evidence | Forbidden markers |
| --- | --- | --- |
| `PENDING` | no evidence; key may be null or reserved | `uploadedAt`, `consumedAt`, `expiredAt`, `failedAt`, `providerDeletedAt`, cleanup confirmation |
| `UPLOADED` | `uploadedAt` and exact evidence | `consumedAt`, `expiredAt`, `failedAt`, `providerDeletedAt`, cleanup confirmation |
| `CONSUMED` | `uploadedAt`, `consumedAt`, exact evidence and canonical StoredFile/asset/version | `expiredAt`, `failedAt`, `providerDeletedAt`, cleanup confirmation |
| `FAILED` | `failedAt`, bounded `failureCode`, no evidence, no file | `uploadedAt`, `consumedAt`, `expiredAt`, `providerDeletedAt`, cleanup confirmation |
| `EXPIRED` | `expiredAt`; either no `uploadedAt` and no evidence (former PENDING), or `uploadedAt` with matching immutable evidence (former UPLOADED); no file | `consumedAt`, `failedAt`, `providerDeletedAt` before confirmed deletion, cleanup confirmation before acknowledgment |
| `CLEANED` | exact reserved key, `providerCleanupConfirmedAt`, no file; preserves either the `FAILED` or `EXPIRED` reason markers and its corresponding uploaded/evidence shape | `consumedAt`; both `failedAt` and `expiredAt`; fabricated `providerDeletedAt` for an already-absent object |

The `FAILED` branch is only reachable from valid `PENDING`; `EXPIRED` is only reachable from valid `PENDING` or `UPLOADED`; `CLEANED` is only reachable from valid `FAILED`/`EXPIRED`. Marker values are immutable after terminalization except the bounded cleanup attempt/ack fields. The SQL guard can enforce local row shape and permitted transitions; cross-table evidence/file predicates require transaction-fresh locked checks and, where necessary, a separate database constraint/trigger in the successor design. Do not claim a row-local CHECK proves cross-table absence.

### State transitions

| Starting state | Condition/atomic DB decision | Provider action | Result |
| --- | --- | --- | --- |
| `PENDING`, no reserved key | rejection or expiry | None: exact object unknown | `FAILED`/`EXPIRED`; never infer key from callback/listing |
| `PENDING`, reserved key, live | definitive rejection under grant lock, no evidence/file | Later exact-key cleanup | `FAILED`; claim/retry eligible |
| `PENDING`, reserved key, expired | DB time `>= expiresAt`, no evidence/file | Later exact-key cleanup | `EXPIRED`; claim/retry eligible |
| `UPLOADED` + exact evidence, no file, live | attachment failure or transient provider fault | None | Remains `UPLOADED`; retry attachment until TTL |
| `UPLOADED` + exact evidence, no file, expired | locked `UPLOADED → EXPIRED`; retain evidence/suffix/key | Later exact-key cleanup | `EXPIRED`; permanently ineligible for attachment |
| `FAILED`/`EXPIRED`, exact key, no file | eligible leased cleanup claim | Exact prelookup/delete/postlookup | Remains terminal until absence is confirmed |
| `FAILED`/`EXPIRED`, confirmed absent | fenced acknowledgment | None | `CLEANED`; confirmation time set; `providerDeletedAt` set only for confirmed deletion initiated by LabOS |
| `CONSUMED` + canonical file/asset/version | attached | None | `CONSUMED`; never rejected/orphan cleanup |
| Any partial or mismatched state | conflict, missing evidence where required, file/key collision, impossible timestamps | None | Fail closed and investigate; do not repair/adopt/delete |

`CLEANED` means a successful exact-key **absence confirmation**, not merely that deletion was requested. An already absent object may become `CLEANED` after an authoritative exact-key lookup returns zero; it has a cleanup-confirmation timestamp but `providerDeletedAt` stays null. A deletion initiated by LabOS may set `providerDeletedAt` only after a successful exact-key deletion response **and** an authoritative post-delete absence check. A returned `success`/`deletedCount` alone, a timed-out call, or an ambiguous lookup is not acknowledgment. `providerDeletedAt` is never set at expiry or claim time. Immutable S001 evidence survives `EXPIRED` and `CLEANED`; it records historical validation, not current provider availability.

### Claim, concurrency, and crash recovery

No PostgreSQL transaction is held over provider network work. Under `FOR UPDATE`, claim one terminal grant by atomically incrementing `cleanupAttemptCount` and setting database-owned `lastCleanupAttemptAt`; the resulting count is the fencing generation. One fixed, bounded lease interval derived from that timestamp allows a crashed worker to be reclaimed. A claimant records only an allowlisted `cleanupFailureCode` and never a provider response/error string. Exhausted/invalid counters fail closed for operator investigation. Claim and acknowledgment each recheck terminal status, exact key, no file, and the claim generation under a row lock. Only the current generation may acknowledge `CLEANED`; a stale worker cannot overwrite a newer outcome. The provider request must use the same exact key captured in the claim. Two workers may exceptionally issue duplicate deletes after a lease timeout: terminality and permanent key binding make this a retry of the same orphan, not an attachment race. The provider's exact-key idempotency/absence behavior must be verified in the successor runtime gate; do not assume a duplicate request succeeds.

This is a database decision followed by an external side effect followed by a separate database acknowledgment, **not** a distributed transaction. Crash before the terminal/claim commit means no deletion is authorized. Crash after claim but before delete leaves terminal state for a later lease retry. Crash or timeout during/after delete leaves outcome unknown and **must not** mark `CLEANED`; retry begins with an exact-key lookup. Crash after confirmed absence but before acknowledgment likewise retries the lookup, then acknowledges. A successful acknowledgment ends retries. If the provider API is unavailable or returns zero/multiple/wrong-key ambiguity in a context that does not prove absence, keep `FAILED`/`EXPIRED`, record a bounded retry code, and back off; never mark `CLEANED` on a guess. A wrong or multiple key response is an integrity incident, not a request to delete every returned key.

Terminalization serializes on the same grant row as the S001 evidence insert (`FOR UPDATE`) and first-attachment write transaction. If finalization wins, cleanup cannot mark live `PENDING` failed; it must await `UPLOADED` expiry. If terminalization wins, finalization's live `PENDING` check rejects. If first attachment wins, cleanup sees `CONSUMED`/`StoredFile` and stops. If cleanup's `UPLOADED → EXPIRED` wins, attachment's locked `UPLOADED`/live check rejects. The **terminal commit must precede provider deletion**, and terminal states must never be revived, even if a provider call fails. Expiry and a failure transition must use conditional updates under the same lock; only one terminal reason wins. The existing generic `expireDue` may end a valid `UPLOADED` retry window, but a Case-specific cleanup writer must recheck evidence/file integrity before deletion. A concurrent generic expiry operation cannot itself authorize deletion.

### Exact provider operation and proof

Use a server-only UploadThing adapter with the configured, attested application token and the persisted single `providerFileKey`; explicitly select `keyType: 'fileKey'`. A bounded exact-key `getFileUrls` lookup, while supported in the pinned SDK, can return one exact result, zero, or unexpected/multiple results. The URL is diagnostic transport data only, not deletion authority, and is not persisted or logged. **Only after the provider capability prerequisite is met** may an authoritative zero prelookup classify `ALREADY_ABSENT`; if exactly one matching key exists, call `deleteFiles` with **one** key, then require an authoritative exact-key lookup proving zero before `DELETED_CONFIRMED`. Unexpected key/count, provider error, uncertain eventual visibility or timeout remains unconfirmed and retryable. No prefix/folder/tenant-wide delete, no arbitrary provider listing, and no delete of a `StoredFile` source are permitted. Current provider docs and SDK do not establish immediate consistency or permanent key nonreuse. A run-owned synthetic probe may test observed delete/lookup behavior, but cannot establish a permanent nonreuse guarantee; obtain an authoritative provider contract/attestation or return a `CAPABILITY_BLOCKER`. The `getFileUrls` deprecation also requires a reviewed replacement before a future SDK upgrade; no silent API substitution.

### Schema sufficiency and backward compatibility

**Additive lifecycle hardening is required before deletion CODE may activate.** The existing columns can carry claim generation, lease start, bounded failure class, and actual deletion time, but they cannot truthfully timestamp an `ALREADY_ABSENT` confirmation; and the installed Case trigger currently allows terminal status revival and arbitrary cleanup-field updates. Add one nullable `providerCleanupConfirmedAt` timestamp (no default/backfill) and a Case-only SQL guard/constraint that enforces the transition and acknowledgment rules above: `EXPIRED`/`FAILED`/`CLEANED` cannot return to `PENDING`/`UPLOADED`/`CONSUMED`; `CONSUMED` cannot enter cleanup; `CLEANED` requires confirmed absence, exact key and no file; confirmation/deletion markers are immutable once set; `providerDeletedAt` implies confirmation and may not be inferred from a zero prelookup. The writer must atomically set outcome-specific fields and status. Existing generic non-Case grant semantics remain untouched. Historical Case grants are not backfilled or automatically cleaned; null checked suffix/key and inconsistent legacy states require explicit investigation. Historical evidence stays immutable. The migration and exact allowed transition matrix require separate CODE/SQL/disposable review; this decision performs no schema edit.

The database cannot verify the external deletion event; the adapter response and exact-key absence check are the application proof. The SQL guard protects the representable state machine and rejects accidental status revival, while transaction-fresh checks and existing uniqueness/locking protect canonical StoredFiles. `providerCleanupConfirmedAt` records when LabOS established absence, not the provider's physical deletion time. This distinction avoids fabricating a deletion timestamp for an object already missing.

### Telemetry and error surface

Use grant ID only inside restricted server operations; ordinary DTOs, user errors and routine logs contain no provider key/URL, bytes, filename, clinical dimensions/hash, decoder details, provider raw diagnostics or tenant-existence hints. Emit bounded stage/outcome classes (claimed, exact absent, delete requested, absence confirmed, retryable provider failure, integrity ambiguity, stale claim, inconsistent canonical state), attempt count and correlation ID under existing operational access controls. Do not record a provider URL as cleanup evidence. Provider object disappearance before cleanup is not a clinical-evidence failure: retain evidence and confirm absence separately.

## Successor verification and remaining uncertainty

The eventual implementation must prove with focused CODE tests and disposable PostgreSQL: every state-table transition and marker shape, keyless denial, exact key/tenant/evidence/file predicates, terminal-state immutability, claim fencing/reclaim, `UPLOADED` expiry with evidence retained, rejection versus transient failure, cleanup races against real concurrent finalization/first attachment/expiry/other cleanup workers, every crash boundary, ambiguous provider responses, repeated calls, stale worker acknowledgment rejection, no canonical file deletion, and generic telemetry. Separate synthetic UploadThing verification can establish observed lookup/delete/postlookup/retry behavior; database tests and a finite synthetic probe cannot prove durable provider nonreuse or authoritative absence. Schema/SQL review and runtime verification precede cleanup activation. Live Case flow, production cleanup, and N-FILE-110 activation remain separate gates.

**Single recommended successor:** separately authorize a bounded UploadThing exact-key ownership/deletion/absence capability decision using current provider documentation or provider attestation, plus a run-owned synthetic probe only for observable behavior. If nonreuse/authoritative absence cannot be established, return `CAPABILITY_BLOCKER` and do not begin cleanup CODE or provider deletion. Additive schema/SQL and writer implementation would then require a later separate gate.

## Independent review

Initial independent read-only V3 review returned `CORRECTION_REQUIRED`: provider key nonreuse/authoritative absence was being attributed to a finite probe, and status-marker consistency was underspecified. The revision made provider capability an explicit blocker and specified the complete marker matrix. Independent read-only V3 rereview returned **PASS | ARCHITECTURE/DECISION**. The reviewer confirmed grant-row terminalization safely serializes with the accepted finalizer and first attachment, and that the unresolved provider guarantee is a `CAPABILITY_BLOCKER` for activation. Provider cleanup runtime remains `NOT_RUN`.
