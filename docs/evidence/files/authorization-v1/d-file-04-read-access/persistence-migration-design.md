Staff additionally require an active authoritative assignment to the Case. Signed URLs are bearer capabilities; issuance audit cannot identify a later downloader or immediately revoke an issued URL. No public clinical link or per-byte application proxy is approved.

All are IMAGE/png, have distinct HTTPS `*.ufs.sh` URL shapes, and have no missing Case or Case/Lab mismatch. URL shape proves neither provider provenance, private ACL, nor ownership. There is no durable platform file identity for these rows.
- The attested development UploadThing app fingerprint is `2e77ac21b101`. The dashboard's approved override save failed; read-only re-attestation remained `defaultACL=public-read`, `allowACLOverride=false`. The cause is unconfirmed, including whether the free plan matters. The Product Owner deferred upgrade and prohibited further toggle attempts, default changes, project substitution, and public Case uploads. This is an unresolved `CAPABILITY_BLOCKER`.
- `CaseAssetFile.documentUrl` is currently required and exposed by ordinary Case readers. ## Proposed durable model

| Entity | Proposed identity and fields | Integrity rule |
| --- | --- | --- |
| `StoredFile` | Immutable platform `id`, canonical `organizationId`/`labId`, source grant ID, provider and opaque object key, closed purpose, verified MIME/size and optional checksum with algorithm, uploader Member, created time, lifecycle/cleanup state. No signed or permanent URL. | Unique source grant and `(provider, objectKey)`; one stored object attaches to at most one Case asset version. Provider key stays server-side. A row is created only from an exact verified `UPLOADED` grant consumed in the final attachment/replacement transaction. |
| `CaseAssetFile` | Existing stable asset `id`, Case/Lab, clinical labels/type; proposed `storageMode` (`LEGACY_URL_UNVERIFIED` or `MANAGED_PRIVATE`) and nullable `currentVersionId`. Keep `documentUrl`/`fileExtension` as nullable legacy compatibility data. | Composite Case/Lab relationship and tenant-aware indexes. Managed assets have a current version and no authoritative URL field; legacy assets have no managed version. Metadata edits cannot implicitly detach or replace a file. |
| `CaseAssetFileVersion` | Immutable `id`, asset/Lab, `storedFileId`, monotonically increasing version number, actor Member and creation time. | Unique `(assetId, versionNumber)` and `storedFileId`; same-Lab relationships to asset and stored file. One mutable `CaseAssetFile.currentVersionId` points to the current immutable version. A transaction inserts the new version and switches the pointer with concurrency protection; prior versions survive. Exact composite foreign keys/deferrability require migration validation. |
| `CaseFileAccessAudit` | Append-only ID, canonical Organization/Lab, actor Member, Case and asset identifiers when resolvable, allowlisted authorization and issuance outcomes/reason, correlation ID, event time, and expiry when issued. | No URL, provider key, token, clinical payload, or arbitrary JSON. Retain identity snapshots without cascade deletion. Audit writer exposes append only; database privileges/constraints and tests must enforce practical immutability. |

The grant proves staging, not durable file ownership. Neither a key, URL, grant ID, nor possession of a prior signed URL authorizes attachment or issuance. A failed final transaction must roll back grant consumption, `StoredFile`, version, current pointer, and asset mutation together. Provider bytes uploaded before failed commit become an orphan handled by a separately approved cleanup policy, not a silently attached file.

## Ownership, read, and audit boundary

Resolve the authenticated actor's active Organization, verified Member, and Organization-linked Lab before resource loading. A trusted Case resolver derives `Case.id -> Case.labId -> Lab.organizationId`; an asset resolves through its Case and same-Lab version/file. Candidate IDs are selectors only. Missing, inconsistent, or cross-tenant facts deny without existence disclosure. Owner/Admin/Manager use the exact approved Authorization V1 Case policy, not role rank. Staff additionally require same-Lab `LabStaff` linked to the Member, `isActive`, and `CaseStaffAssignment` for this Case. The effective `case.read` policy and `case.asset.add`/replacement policies still need registration and focused tests; deny while unsupported.

For each signed-read request, freshly authorize, then resolve the current managed version and provider object, issue a signed URL valid for at most the approved 300 seconds, and append the issuance outcome before returning the URL. Record denied attempts using only identifiers already safely known at the denial point. Audit write failure must fail closed for delivery; an issued-but-undelivered URL may exist briefly at the provider, so the audit outcome must distinguish that case. No signed URL enters persistence, telemetry, logs, or ordinary DTOs. The audit foundation is limited to this Case issuance event, not the M6 audit program.

## Saved-DRAFT and asset operations

The existing new-Case flow already offers **Save Draft** after patient selection. The smallest proposed sequence retains that explicit action: authorize and persist the Case as `DRAFT` under the canonical Lab, return its saved ID, then enable Case-targeted clinical staging. No unsaved browser-only Case, targetless grant, automatic Case creation, or new workflow status is needed. Staging and final attach revalidate Case, tenant, permission, and applicable draft state. Callback verification marks the grant uploaded; final attach consumes it once and creates `StoredFile`, stable asset, and version 1 in one transaction. The existing draft-save and Case-update paths must stop accepting raw URLs and deleting/recreating managed or legacy asset rows. Preserve asset metadata through ordinary Case saves; give actual asset operations explicit commands.

For N-FILE-111, stage against both authoritative Case and existing asset identity, revalidate that the asset still belongs to that Case/Lab and that replacement permission applies, then create a new `StoredFile` and version and atomically change only the current-version pointer. No prior provider identity is overwritten. Omission, empty URL, or absent grant cannot remove an asset. Removal and provider deletion remain separate, unapproved operations.

## Legacy handling and migration proposal

1. Re-run a read-only preflight inventory before any authorized migration; reconcile drift from the observed three-row baseline and Case/Lab consistency before writing.
2. In an additive migration, introduce tenant-aware uniqueness/foreign-key support, `StoredFile`, `CaseAssetFileVersion`, and `CaseFileAccessAudit`; add the storage mode and nullable current-version pointer to `CaseAssetFile`. Make the existing required `documentUrl` nullable only to permit managed rows with no persisted provider URL. Validate generated SQL, indexes, constraints, and rollback on a non-production target before application.
3. Mark only verified existing URL-only rows `LEGACY_URL_UNVERIFIED`, preserving their IDs, URLs, and clinical metadata unchanged. Create no `StoredFile` or version for them. Do not parse `*.ufs.sh` URLs into provider keys or silently backfill tenant/provenance/ACL claims.
4. A later, separately approved read cutover returns safe metadata plus the approved unavailable-pending-verification indicator for unreconciled rows; it never falls back to the raw URL or issues signed access based on it. Existing historical bytes are not claimed private by the migration. Individual reconciliation needs independently verified object identity, canonical ownership, ACL, and content integrity; each row needs an authorized record and method. No deletion is proposed.
5. Enable managed writes and signed reads only after implementation, provider capability, and runtime gates pass. Retain legacy compatibility columns until a separate contract decision. Rollback is a feature disable of new staging/attach/replace/read boundaries while retaining additive records and audit. After managed writes, do not destructively down-migrate or re-expose raw clinical URLs as a rollback.

Current and superseded file bytes, immutable version records, and issuance-audit records are retained. No automatic purge is approved. A future cleanup requires separate Product Owner authority and must prove no current reference, be idempotent/retryable, and retain required history. Orphan handling, provider deletion, individual legacy reconciliation, and any audit-retention change are distinct future decisions. Expired unattached grant/orphan handling is separate from historical-version retention.
