## Provider capability and limitation

Supabase's current [Postgres role guide](https://supabase.com/docs/guides/database/postgres/roles) documents custom LOGIN roles and grants, recommends separate service users, and identifies its `postgres` role as administrative. Its [connection guide](https://supabase.com/docs/guides/database/connecting-to-postgres) recommends transaction pooling for serverless runtime and direct connections for migrations; transaction mode does not preserve session state across transactions. The [connection endpoint guide](https://supabase.com/docs/guides/database/connecting-to-postgres) describes custom-role usernames through the shared pooler. Its [custom-role troubleshooting guide](https://supabase.com/docs/guides/troubleshooting/fatal-password-authentication-failed) says custom LOGIN roles work with direct and Supavisor connections, while pooled password changes can have brief cache lag. These are documented **provider capabilities**, not target-specific attestation.

Supabase's generic [Prisma guide](https://supabase.com/docs/guides/database/prisma) demonstrates a privileged Prisma user with `BYPASSRLS`, `CREATEDB`, schema CREATE and broad grants. That example is suitable to compare with a migration identity, **not** to copy into the restricted LabOS application runtime. Supabase's [custom-role privilege guidance](https://supabase.com/docs/guides/troubleshooting/custom-role-inherits-privileges-that-were-not-explicitly-granted-ddaa1c) warns against inheriting `postgres`/Supabase roles and against treating mutable session settings as access control. PostgreSQL [role membership](https://www.postgresql.org/docs/current/role-membership.html) permits inherited or SET-able owner rights, so both paths must be absent. The hosting documentation makes the architecture plausible; production role creation, function ownership transfer, pooler authentication, RLS and Vercel secret routing remain unverified.

| Ordinary application runtime | Own `DATABASE_URL` through approved Vercel/server connection; LOGIN, CONNECT database, USAGE of required app schemas, per-table SELECT and only required INSERT/UPDATE/DELETE for Prisma and Better Auth; USAGE on specific sequences only if actually used. Existing SQL triggers must run with this role. | Table/schema/function ownership or owner membership; `CREATEROLE`, `CREATEDB`, `BYPASSRLS`, REPLICATION, DDL/schema CREATE, TRIGGER/ALTER/DISABLE rights, grant options, ACK EXECUTE, `DIRECT_URL`. |
| Cleanup worker | Separate server-only LOGIN/connection secret, CONNECT/USAGE, SELECT on exact grant/allocation/canonical-reference tables, column-scoped UPDATE of claim/lease/retry fields, EXECUTE on the single ACK function. Needed provider credentials are separate from DB grants. | Owner/function-owner membership, `CREATEROLE`, `BYPASSRLS`, table-wide UPDATE/DELETE/TRUNCATE, DDL, arbitrary function EXECUTE, normal application identity or migration URL. |
| ACK function owner | `NOLOGIN` role that owns only the narrow function in a locked schema and has SELECT on exact guard tables plus the minimum grant-column UPDATE required by ACK. Function executes with its privileges. | LOGIN/credential, owner membership in runtime roles, `CREATEROLE`, `BYPASSRLS`, table/schema ownership, generic mutation or broad EXECUTE grants. |

Per-table application privileges must be enumerated from actual Prisma and Better Auth calls before implementation; a blanket grant on all present/future public objects is **not** the approved minimum. Better Auth uses the same `generalPrisma` connection for AuthUser, Session, Account, Verification, Organization/Member/Invitation and related plugin operations; LabOS application repositories also write domain tables. The restricted role must pass sign-in/session refresh, organization onboarding/membership, existing file and Case workflows, and representative authorization tests. Granting table DML does not replace LabOS tenant authorization: development currently has no public-table RLS. If the intended target has RLS, policies for the new non-owner roles must be inventoried before any cutover. Do not add `BYPASSRLS` merely to make tests pass. Supabase Data API `anon/authenticated/service_role` grants must be inspected separately; the development grant observation is not production proof.

Current public schema has no sequences, but a future migration may add identity/serial columns. Sequence `USAGE` for `nextval` is separate from table INSERT; grant only required sequences. PostgreSQL [default-privilege rules](https://www.postgresql.org/docs/current/sql-alterdefaultprivileges.html) apply to the **object-creating role**, not roles from which it inherits privileges. Therefore each future LabOS migration must include audited per-object grants (or approved migration-owner default ACLs) for application/worker roles; `_prisma_migrations` remains migration-only. Function EXECUTE defaults require explicit revocation from PUBLIC and any direct grants, including Supabase API roles, for the ACK function.

## ACK trust boundary and pooling

The accepted A1 design selects one ACK writer: a server cleanup worker performs exact semantic-port `ABSENT` inspection and then calls the DB function with grant ID and claim generation only. No caller key, URL, tenant or `absence=true` parameter. The function locks the grant and rechecks terminal status, same live generation/lease, exact permanent allocation, elapsed write-capability fence and no canonical StoredFile/version/current reference; it atomically writes `CLEANED` and confirmation. PostgreSQL cannot itself prove the provider result, so the worker identity is the remote-attestation authority. A normal application role and direct DML must be denied.

Function ownership must be moved to a distinct `NOLOGIN` owner with no ownership of the grant table; the table owner remains controlled by migration operations. Place the function in a schema with no CREATE privilege for runtime, worker, PUBLIC or Supabase API roles. Use schema-qualified table/function references and `SECURITY DEFINER SET search_path = pg_catalog, <locked_schema>, pg_temp`, with temporary schema last and no writable schema on the path. [PostgreSQL function security](https://www.postgresql.org/docs/current/sql-createfunction.html) and [Supabase function guidance](https://supabase.com/docs/guides/database/functions) require this caution. In the same controlled install transaction, revoke ACK EXECUTE from PUBLIC and any direct grants, grant only the cleanup login, and verify that app/worker cannot `SET ROLE` or inherit table/function owner, replace the function, alter/disable trigger, create shadow objects, or change owner privileges. `CREATEROLE` and table ownership remain excluded. Avoid a session GUC or `SET ROLE` as an ACK authorization signal: a pooled connection loses session state and a normal client may set its own GUC. The SQL function call and DB checks must be contained within one transaction and work under the actual pooler mode.
