# D2-V2 — Initial Vercel build diagnosis

The Product Owner reported creating the `lab-os-verification-deployment` Vercel project, assigning the local `.env` `BETTER_AUTH_SECRET` to Production and Preview and the `.env.local` value to Development, then observing build errors. These are user-performed changes; the agent did not create the project, set variables or deploy. No secret values were read from Vercel or recorded here.

Authenticated Vercel project/deployment reads on 2026-10-10 identify project `prj_wJiC2MYXpqpE9W4JIgxQnf8QfhqA`, Next.js, Node `24.x`, and failed Production deployment `dpl_Hxd4tcLbKLYbp81LpHW5nDNumzfn` from `alilefta/LabOS` `main` commit `6796fda6b18e67beb0b24340b0703bd34a27d4b9`. The project read reported `live: false` and Vercel Authentication enabled for `all_except_custom_domains`. This is setting metadata, not a successful protected HTTP test. No application deployment succeeded.

The build log's first material failure is module resolution for `@/generated/prisma/client` in `actions/team/staff-settings/update-staff-compensation.ts` and `lib/safe-action.ts`; `next build` exited 1 (`ENOENT`). The deployed commit's `package.json` sets `build` to `next build`, and no `postinstall` generation hook exists. Its Prisma schema generates into `../generated/prisma`, while `.gitignore` excludes `/generated/prisma`. The deployment log shows package installation and `next build`, without a successful `prisma generate`. This explains the missing generated client. The log does **not** identify `BETTER_AUTH_SECRET` as the build failure. Later build/type/native failures are unknown because compilation stopped here. The deployed `main` commit differs from the dirty local checkout; local uncommitted changes were not in this deployment.

## Environment boundary finding

An authenticated Vercel environment-key inventory was read with decryption disabled. It showed the following names scoped to Production and Preview: `DATABASE_URL`, `DIRECT_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `AXIOM_TOKEN`, `AXIOM_DATASET`, `AXIOM_EDGE`, `LABOS_AUTHORIZATION_MODE`, `UPLOADTHING_TOKEN`, `UPLOADTHING_DEVELOPMENT_TOKEN`, `LABOS_R2_ACCOUNT_ID`, `LABOS_R2_BUCKET`, `LABOS_R2_ACCESS_KEY_ID`, `LABOS_R2_SECRET_ACCESS_KEY`, `LABOS_R2_NON_PRODUCTION`, `LABOS_R2_CONFORMANCE_RUN`, and `LABOS_R2_CLIENT_ENDPOINT`. Development held `BETTER_AUTH_SECRET`. These are **names and target scopes only**; effective values, database identity and R2 bucket binding were not attested.

The accepted [D2-R1 design](../../plans/deployment-d2-r1-hobby-free-feasibility-20261008.md) expressly prohibits `DIRECT_URL` and any migration-owner credentials in Vercel builds or functions, and requires an isolated restricted verification runtime identity. Vercel exposes project environment variables to builds and functions ([provider documentation](https://vercel.com/docs/environment-variables)). The presence of `DIRECT_URL` in Production and Preview therefore conflicts with the accepted boundary regardless of its undisclosed value. The broad variable import also requires a key-by-key verification that `DATABASE_URL`, R2 credentials and other enabled integrations belong only to the isolated verification environment. Do not infer from names that the values are safe or unsafe. `UPLOADTHING_DEVELOPMENT_TOKEN` and R2 conformance flags need explicit necessity review before any successful deployment.

## Safe correction gate

The likely build correction is to run Prisma client generation before `next build`; [Prisma's Next.js/Vercel guidance](https://docs.prisma.io/docs/orm/v7/more/troubleshooting/nextjs) recommends explicit generation during deployment builds. Prisma's [configuration reference](https://www.prisma.io/docs/orm/v7/reference/prisma-config-reference) separates generation from database-requiring migration commands. This is a proposed fix, **not run** on Vercel and not permission to add `DIRECT_URL` to satisfy a build. First remove the prohibited Vercel `DIRECT_URL` target scopes and attest the isolated restricted `DATABASE_URL`/R2 bindings under separate authority. Then approve a bounded build-command or source correction and a new protected diagnostic build. A build pass would not by itself attest database role isolation, migrations, native S001, Better Auth callbacks, HTTP protection or N-FILE-110 activation.

No application code, project settings, environment values, Supabase roles/data, R2 resources, build command, deployment or Git state was changed by this diagnosis. A1-I1 remains `BLOCKED_DECISION`; N-FILE-110 remains inactive.

Independent V3 `PASS | CHECKPOINT` read-only review confirmed the deployed-commit generation/ignore chain, the log-attributed first `ENOENT`, the D2-R1 `DIRECT_URL` conflict, working local links, and the absence of disclosed secret values or successful-deployment claims. The reviewer made no edits or provider calls.
