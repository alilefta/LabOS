## Provider boundary: amended architecture

R2 is the V1 **implementation** of LabOS object storage. It is not a Files/domain concept. The accepted Files lifecycle, authorization, checked suffix, S001, application SHA-256, immutable evidence, StoredFile ID, Case asset/version, attachment transaction, `CONSUMED`, cleanup state machine and private-open authorization remain above the provider boundary. UploadThing keeps its existing higher-level ingestion path during gradual migration; it is not made to implement the new low-level contract for symmetry.

Dependency direction:

```text
Case UI/routes → Files application orchestration → authorization + grant/evidence/asset repositories
                                  │
                                  └→ LabOS ObjectStorage semantic port
                                             ↑
                                  R2 adapter → AWS SDK v3/R2 endpoint/config

Live non-Case UI/routes → legacy UploadThing ingestion → existing grant/domain commands
```

The server-only semantic port exposes only the capabilities LabOS requires: issue a time-bounded **exact-key create-only** write capability; inspect one exact object; retrieve one exact object with a hard byte bound, cancellation and normalized failure; issue a time-bounded exact-key read capability; delete one exact key; and authoritatively classify exact-key presence/absence through the direct private provider interface. Calls take server-owned exact storage identity and policy bounds, never caller-supplied bucket, endpoint, raw AWS command or provider URL. The returned upload/download capabilities are opaque, short-lived bearer values delivered only through the authorized route; they are never durable identity, evidence, telemetry or logs. The interface promises required semantics, not that every S3-compatible provider supplies them automatically. The R2 adapter owns conditional `PutObject`, SigV4, SDK commands, endpoint/account/bucket, ETag, response shapes, retries and provider-error normalization. Domain imports only the semantic port and closed result/error types. No R2 or AWS SDK types cross that import boundary.

`objects/{uuidv4}` or stronger opaque randomness is allocated and durably reserved by LabOS, never by R2. The permanent nonreuse rule belongs to LabOS across adapters, deployments, deletion and future provider changes. R2's conditional create is a separately verified defense against overwrite. R2-specific error codes never become lifecycle states or client messages. For each future provider, a conformance gate must establish create-only browser write (including signed-header enforcement), private exact HEAD/GET, bounded streaming, exact-key delete and authoritative absence, signed read, URL expiry behavior and relevant consistency. If a provider cannot meet a required semantic capability, the adapter is not accepted; the domain contract is not weakened implicitly.

The smallest V1 persistence model is `StoredFileProvider.OBJECT_STORAGE` (and the same value on `FileUploadGrant.provider` and `CaseClinicalUploadEvidence.provider`) plus the existing immutable LabOS-owned `providerFileKey`/`providerObjectKey`. Despite the legacy enum name, this value denotes a logical backend class, **not R2 physical provenance**. `UPLOADTHING` remains the historical higher-level ingestion label. `StoredFile.id` remains canonical. The physical vendor is deployment/adapter provenance in controlled configuration and migration evidence; no R2 endpoint, account ID, bucket, AWS command, SigV4 detail, ETag or provider diagnostic is added to domain records. One private object-store bucket per environment is the V1 configuration assumption. Do not add a storage-location table now. A requirement for multiple simultaneous stores, per-object routing, independent residency or changed keys would require a separately approved location model before mixed writes.

| Persistence question | Answer for V1 |
| --- | --- |
| Does Files/domain require vendor identity? | No. It needs a stable backend dispatch class, exact LabOS-owned key and access classification. Authorization and lifecycle must not branch on `R2`. |
| Is R2 identity physical provenance? | Yes. Which physical service held bytes is infrastructure/migration provenance, not the immutable clinical validation meaning of the grant/evidence/file tuple. |
| Would a storage-location ID improve portability? | It would help if R2 and S3 coexist per object, buckets change independently, or keys must change. Those requirements are absent from this V1 whole-backend model. |
| Would adding a location table now be justified? | No. It would add an extra identity, FK and migration surface without solving a current requirement. Record the single-active-backend assumption and return for decision if it fails. |
| Which database fields change on a same-key full R2 → S3 cutover? | **None.** The following paragraph lists the grant, evidence, StoredFile and Case fields that remain fixed. Only adapter/configuration/credentials and physical-object reconciliation change. |

**Future R2 → AWS S3 migration surface:** assuming AWS S3 passes the semantic conformance suite, LabOS copies each object under its **same LabOS key**, verifies exact length and application SHA-256, and reconciles every referenced key including terminal/cleanup states. A whole-backend cutover must stop issuing R2 write capabilities, wait for every outstanding R2 presigned PUT to expire plus clock skew, perform a final source/target reconciliation, then switch adapter configuration/credentials only after complete target attestation; an online dual-store protocol would need separate architecture approval. Old signed reads expire under their existing short TTL; R2 objects are not deleted merely because configuration switched. Under this whole-backend same-key cutover, **no database field changes**: `FileUploadGrant.provider`, `providerFileKey`, status/expiry markers; `CaseClinicalUploadEvidence.provider`, `providerObjectKey`, profile/hash and immutable validation fields; `StoredFile.id`, `provider`, `providerObjectKey`, `providerAccess`, checksum; `CaseAssetFile`, `CaseAssetFileVersion` and their current-version pointers all retain their values. Neither grant lifecycle, Case authorization, S001, attachment nor cleanup semantics are rewritten. Historical physical R2 provenance remains in the migration manifest/audit rather than mutating immutable validation evidence. If same-key copy, complete cutover or equivalent semantics cannot be established, **stop for a new location/reconciliation decision**; do not relabel only some objects under `OBJECT_STORAGE` or silently rewrite evidence. Existing UploadThing-backed rows follow their separate later migration/disposition gates.
