## Pre-implementation findings (historical)

`actions/invoices/create-invoice.ts` runs `actionClientWithLab` with `requiredLabRole: "MANAGER"`, then manually calls V1 `invoice.create` before `tenantPrisma`. The accepted fixed role bundle includes Owner/Admin/Manager, so the old gate prevents the approved Admin expansion. No A-089 entry exists yet in the registered action-boundary adapter.

The transaction reads tenant/Clinic-filtered eligible unbilled Cases and creates an Invoice plus Case links. It does not resolve the submitted Clinic as an authoritative tenant Clinic and does not update `Clinic.currentBalance` for SENT. It uses JavaScript `Number` for subtotal/discount/total and snapshots, without explicit HALF_UP rounding or persisted accounting-identity protection. It uses the default transaction isolation. `InvoiceCase.caseId @unique` is an important existing backstop against two successful claims of the same Case; do not weaken it. Neither that constraint nor the Lab sequence increment proves every financial invariant. `createInvoiceAction` already keeps public token issuance/disclosure separate, returns safe committed amount/currency metadata, and its UI calls `N-FIN-PL-001` only after SENT commit.

## Minimum implementation boundary

1. Register A-089 in `modules/labos-authorization/action-boundaries.ts` and the existing `lib/safe-action.ts` registered adapter. The registry owns `CreateInvoiceInputSchema`, action name, fixed `invoice.create` permission, Organization scope, and a closed `invoice.create` operation intent with validated Clinic/Case identifiers. These identifiers are untrusted references, not authoritative ownership or price facts. Add the typed intent to `operation-intents.ts` and only the policy wiring needed to validate that intent. Use `actionClientWithAuthorization('A-089')`; remove the authoritative `requiredLabRole` and manual `can()` check. No new permission, role expansion, global-mode change, or telemetry payload field is needed. Missing registration, invalid input/intent, missing tenant, and denial fail before domain work and tenant Prisma. Preserve redacted telemetry.
2. Within one Serializable mutation transaction, resolve the Clinic with trusted `labId` and submitted `clinicId`; reject missing/foreign Clinic without revealing existence. Re-read every requested Case by trusted Lab and resolved Clinic, verify eligible `COMPLETED`/`DELIVERED` status and no existing InvoiceCase link, and reject duplicate/missing/foreign/ineligible IDs. Use transaction facts to set Case snapshots and totals. Keep the Lab sequence update inside the transaction and preserve existing Invoice numbering, dates, billing terms, and state rules.
3. Sum authoritative Case prices using `Prisma.Decimal`, round subtotal to the Invoice's two-decimal scale with `ROUND_HALF_UP`, round percentage discount `ROUND_HALF_UP`, derive `total = subtotal - discountAmount` from those rounded values, and set `amountDue = total`, `amountPaid = 0`. Preserve the existing bounded 0–100% discount and reason requirement. Do not reprice other Invoices or change currency storage.
4. Create Invoice and Case links, then increment the resolved Clinic's `currentBalance` by the committed amount due **only when status is SENT**, all in that transaction. DRAFT gets no credit. On any conflict or failure, the sequence change, Invoice, links, and balance change roll back together. A repeated submission involving the same Cases must not produce a second successful Invoice or second credit. Preserve `InvoiceCase.caseId @unique`. If retrying a recognized serialization conflict, retry the entire transaction a bounded number of times with fresh Clinic/Case facts; never replay after an acknowledged success or treat an unknown transport failure as proof of rollback. Do not add request-idempotency persistence without a separate decision.
5. Preserve the ordinary result's safe `id`, `invoiceNumber`, committed `amountDue`, and authoritative currency. Keep it bearer-free. Leave `N-FIN-PL-001`, the create/edit share UI handoff, public reader, A-097, payment/cancel/void paths, and audit migration unchanged.

Likely production edits are limited to the create action, registered-boundary/intent/adapter definitions, and only necessary policy validation. The existing Prisma schema and migration require no change for this bounded correction.

## Verification and acceptance claims

- **Authorization:** Owner/Admin/Manager allow; Staff/unknown role, missing membership, invalid tenant, malformed/duplicate IDs, missing registry/invalid intent, and foreign Clinic/Case deny before protected domain work. Confirm no legacy MANAGER dependency and redacted telemetry.
- **Financial:** DRAFT leaves Clinic balance unchanged; direct SENT increases the trusted Clinic balance exactly once by persisted amount due. Test fractional-cent discounts (including subtotal 0.05 with 10%), `total = subtotal - discountAmount`, snapshots, zero/100% discount, and existing date/numbering behavior.
- **Transaction:** On fresh disposable PostgreSQL, use real overlapping transactions for the same Case set and verify at most one success, one InvoiceCase claim per Case, one Clinic credit, and no partial Invoice/link/balance/sequence changes after injected failure. Test Case status/price/billing changes between authorization and transaction, foreign Clinic/Case and inconsistent relationships, and bounded serialization retry behavior. Preserve unique constraint.
- **Handoff:** DRAFT does not request sharing; SENT invokes only the separate authorized share action after committed create. Ordinary create response contains no token. Existing sharing failure/retry and committed amount/currency handoff tests remain passing. Browser evidence should be run when an isolated authenticated local application/database fixture is available; source-level UI tests alone do not establish browser behavior.
- **Checks:** Focused financial/authorization regressions, TypeScript, lint/architecture checks, `git diff --check`, and independent V3 code plus disposable PostgreSQL concurrency review.
