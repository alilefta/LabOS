# N-FILE-110 activation readiness — Product Owner-approved plan

This is the **Product Owner-approved governing plan**, not implementation or activation authority. A1 design/documentation only is separately authorized; A2–A5 require later authority. R2-06 is `CLOSED | PASS CHECKPOINT` and the Product Owner approved `ELIGIBLE_FOR_ACTIVATION` for its reviewed technical scope. Neither decision activates N-FILE-110, makes clinical uploads generally available, authorizes cleanup implementation, or approves deployment. Every implementation, runtime target, provider/database operation, feature exposure and deployment below needs its own Product Owner authority. The current server constant `CASE_OBJECT_STORAGE_UPLOAD_ACTIVE = false` still returns 404 at both Case intent and completion routes.

## Verified starting point and limits

- R2-01 through R2-06 are accepted checkpoints. R2-06 proved the complete synthetic Case/R2/isolated-PostgreSQL chain under real Linux x64, Node 24, N-API 10 production S001 identity, with exact three-object absence and independent V3 runtime/checkpoint PASS. Its first telemetry assertion failure, correction, and checkpoint-documentation correction remain in the [R2-06 packet](../../evidence/files/authorization-v1/r2-06-production-s001-case-runtime/packet.md).
- Actual Edge browser conditional PUT/CORS belongs to R2-05; R2-06 used Node fetch and did not rerun that browser claim. Browser consumption of a private signed GET, activated HTTP/UI flow, and normal-development Case mutation are `NOT_RUN`. The last is an accepted authority limitation because disposable PostgreSQL supplied verification. The optional whole-snapshot TypeScript check is `INCONCLUSIVE` after Node heap exhaustion.
- New Case objects use the semantic ObjectStorage port and logical `OBJECT_STORAGE` identity; R2 is an infrastructure adapter. Existing UploadThing ingestion for non-Case boundaries and historical `PUBLIC_READ`/`MANAGED_PUBLIC` rows retain their accepted paths. No new R2 capability URL, key, ETag or vendor detail becomes normal DTO or audit identity.
- The currently reachable Case upload intent/completion HTTP handlers are server-gated inactive. The private-open route already exists, but the Case asset vault currently renders `MANAGED_PRIVATE` as “Content unavailable”; only `MANAGED_PUBLIC` has an open link. The older new-Case `CaseFileUploadZone` still calls UploadThing; route/UI activation must identify the saved-DRAFT Case entry point and must not silently make that older control a new clinical upload path.
- The historical rejected/orphan cleanup decision is a design for UploadThing-backed Case keys. It establishes useful LabOS terminalization and no-canonical-file principles, but its provider-specific key/absence blocker and SQL proposal are not automatically an OBJECT_STORAGE implementation. The R2-02 allocation ledger, expiry fence and R2-01 exact absence capability must be reconciled into a separately reviewed OBJECT_STORAGE cleanup successor.

## Claim and risk map

1. **No bypass on activation:** server gate, trusted session/tenant/Member/Case facts and transaction-fresh rechecks hold across both HTTP routes and attachment/open. Prove denied requests cause no provider operation or capability disclosure.
2. **No new undeletable orphan path:** every terminal rejected/expired unconsumed object has a bounded, retryable, exact-key cleanup route with durable expiry fence and authoritative absence. Prove cleanup never deletes a canonical CONSUMED file or races with attachment.
3. **Real user path works:** actual browser performs upload and signed private GET after the complete HTTP flow; accepted synthetic R2-06 composition is the baseline, not a substitute for this missing claim.
4. **Buildable deployment profile:** TypeScript and production build pass with real S001/native identity; R2-06 optional check remains `INCONCLUSIVE` until this gate passes.
5. **Reversible exposure:** disabling new intent cannot silently abandon existing capabilities or remove access to accepted historical/current files. Monitoring detects stuck grants, provider failures and cleanup lag without bearer disclosure.

No production-profile or general clinical availability claim follows from an isolated test. Existing historical UploadThing assets remain readable under their accepted mode; no non-Case migration or UploadThing removal is included here.

## Separate Product Owner decisions and authority requests

1. Approve or revise this gate ordering, particularly whether accepted OBJECT_STORAGE cleanup implementation/runtime must pass before any general Case upload exposure. The recommendation is **yes** because rejected/expired objects otherwise have no accepted terminal cleanup path.
2. Select the exact saved-DRAFT Case UI entry point and initial audience/environment; specify the fate of the older new-Case UploadThing control for this purpose. Keep general access off until separately approved.
3. Approve the rollback rule for in-flight PENDING grants and already issued PUT capabilities. Recommended behavior: block new intents/issuance, continue only safe completion/drain or terminalization under accepted lifecycle, and preserve authorized private read of CONSUMED files.
4. Authorize each implementation/schema/install and disposable runtime target separately, then approve monitoring owner/thresholds, cleanup schedule, rollout/deployment target and final switch action. Production provider/database/credential actions require explicit target-specific authority.
